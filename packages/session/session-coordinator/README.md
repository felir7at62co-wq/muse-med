# @deepseek-ai/dsh-session-coordinator

English | [中文](README.zh.md)

## Summary

Compose this optional Host plugin with a routing-only preset. The Main Session searches the local profile owner's ordinary conversations, checks candidate summaries, and chooses an idle existing Session or a fresh worker. Workers keep their ordinary tools, history and presets. The separate task ledger tracks dispatch and execution revisions; receipt delivery does not imply completion or human acceptance.

## Use this package

Mount the default export on the Host and `/worker` alongside ordinary tools. Compose `/main` only inside the configured Main preset. Muse offers `main-session` and retains `short-drama` as its default. The optional [Main Session navigation plugin](../../client/ui-session-coordinator/README.md) provides the retained Main entry and startup navigation. Worker Sessions keep their native sidebar rows; results return through Main chat messages. Removing the Host plugin retains ledger files and ordinary Session history.

`mainPreset` and `workerPreset` select distinct roles; `searchLimit` bounds search rows and `readChars` bounds each raw history page, allowing one oversized event intact. `noteChars` bounds each routing note (`instructions`, `reason`) Main writes, and `summaryChars` bounds a worker report summary. `maxWorkers`, default 3, bounds coordinator assignments executing at once; beyond it, a dispatch that needs a fresh worker waits. Search and read are local profile-owner capabilities across working directories. They never open remote accounts or grant access to another user's profile. The Remote methods require global owner access; scoped guest grants do not authorize the task directory.

When the Host also mounts [`dsh-session-activity`](../session-activity/README.md), each `coordinator_sessions` row gains a `status` line as the session list shows it (running, idle, waiting for an answer or approval, last turn failed, with the latest tool and running jobs and subagents), and the coordinator watches the worker of every assignment that holds a `maxWorkers` slot, releasing the watch when the assignment leaves those states or the activity service is replaced. Main then receives status digests between receipts: changes wait for Main's next step, and a worker waiting for input, a failed turn or a stall wakes Main. Main's prompt then adds that digests need no reply or polling, that `coordinator_read` holds the details, that an attended Main points the user to a waiting worker, and that an unattended Main notes attention items and waits for the receipt. Without that plugin rows carry no status, Main receives receipts only and its prompt is unchanged.

Set `unattended` for a deployment in which nobody answers questions, such as a scheduled daily run. Main can then dispatch from its latest schedule reminder as well as from a human message, and neither Main nor any member of an assigned worker's execution tree can call `humanTools`, which defaults to `ask_user_question` and `exit_plan_mode`. When a task's latest revision ends `needs-report`, `failed`, `blocked` or `needs-input`, or ends `interrupted` once its worker is quiescent, the coordinator re-dispatches it to a fresh worker in the same directory. After `redispatchLimit` consecutive automatic re-dispatches, default 1, it records an `attention` reason and time on that revision instead. `taskRoot`, an absolute directory, gives every task its own folder `<taskRoot>/<task id>`: dispatch creates it before the task's first fresh worker, and rejects another `cwd` or reuse of a Session in another directory. Bound subagents inside each worker with the subagent plugin's `maxActiveSubagents`, default 8: every worker roots its own subagent tree, so `maxWorkers` fresh-worker assignments run at most `maxWorkers` × `maxActiveSubagents` subagents at once. That setting applies to every root Session on the Host.

Main's positive capability list admits coordination tools, `ask_user_question`, `show_view` and `visualize`. The fixed `coordinator_display_skill` loader reads only the model-invocable `visualize` Skill through the native registry; general `skill`, file and shell tools remain unavailable. An execution guard also rejects other tools, including late registrations and the PTC transport. Workers are created through the ordinary Session controller, outside Main's restrictive scope. Main routes requests, relays receipts and worker questions, and handles stop requests; planning, research, writing, file changes, downloads, generation and review remain worker tasks. The worker brief and `coordinator_report` guide a worker to report `needs-input` with one question in its summary instead of asking in its own chat, and Main relays that question to the user. Workers keep `ask_user_question`, because short-drama content-listening acceptance and budget approval accept only an answer to a question asked in the same Session.

Main's system prompt limits it to routing: it does not restate or add requirements, does not read worker history before reconciliation, and ends its turn after dispatch instead of polling. It asks the user to restate in one message a request spread across earlier messages, relays a `needs-input` question as text rather than a card, dispatches the revision after the user's reply, and stops reconciling a task whose reconciliation ended without a report. It explains that a fresh-worker dispatch returning `dispatching` is queued and starts automatically, so Main tells the user instead of dispatching again. It also says that fresh workers share Main's directory, that `cwd` names another folder rather than a project subfolder, and that a change to drafts an unfinished task is editing is routed as that task's revision. It prioritizes readable chat presentation: concise conclusions, grouped information and task-report cards after dispatch and when a task ends. It guides the model to use structured cards for comparisons, lists, choices and forms, while keeping short answers as text. This is model guidance; task notifications do not create cards without a display-tool call. With `unattended`, the prompt instead says that nobody answers, that a schedule reminder can carry the request, that each listed independent object gets its own task, and that the coordinator resolves unresolved tasks while Main records receipts without asking. With `taskRoot`, it says that each task works in its own folder and that only a worker of the same task is reused.

Bounded routing notes are tagged relay context, and the worker brief labels them as notes, not requirements. Only Host-verified original human messages retain their original user attribution and unchanged content; coordinator-authored notes never become human authorization. Dispatch includes the latest Main human message and its attachments unchanged, the message recorded by each earlier revision, the routing notes and the saved video-model key when present. A fresh worker receives Main's dialogue-model selection; reusing a worker preserves its dialogue model. A saved video selection is applied through the worker's native selection service before input delivery. Missing or unavailable selection support rejects delivery instead of silently defaulting.

An existing worker must be idle, have no pending input or live owned jobs, and have no unsettled coordination task. Archived Sessions and subagents are reference-only. The agent chooses another worker when reuse is unavailable. A dispatch revision requires the expected revision and settlement or an explicit stop of its predecessor; it cannot silently steer over an in-flight assignment. Direct human input in a reserved worker invalidates its previous report and notifies Main without cancelling the new user work.

`coordinator_show_report` captures owner-verified task IDs, current revisions, worker Sessions, status and native file declarations in versioned tool-result metadata. Omitted or empty IDs select unsettled tasks first, then recent ones; `searchLimit` also bounds reports, with explicit total and truncation fields. `coordinator_tasks` returns routing rows in the same order without a card. Each row counts presented files instead of listing them; the serialized list is bounded by `readChars`, and a row that does not fit is omitted with `truncated` set. Dispatch, reconcile and stop return one routing row for the latest revision. For report cards, the combined serialized model result and metadata are bounded by `readChars`; only complete task receipts are retained, and an oversized first task fails instead of cutting its summary or files. Unknown, foreign, duplicate or excessive IDs fail. The model cannot provide completion flags, percentages or artifact paths. The Client renders inline cards and can follow the same captured revision through the existing task watch; later revisions never replace an earlier receipt.

The Muse spider entry below New Session opens one retained Main Session per profile in Muse's existing default Workspace. Creation goes through the native Workspace and Session controllers; repeated clicks and plugin restarts reuse its stable identity. Workers keep their selected project directories.

`coordinator_reconcile` requests verification of an idle retained worker without requiring Main to read its history. It checks the expected task revision, records the worker's current log position, and rejects an optional `expected_worker_seq` that differs from that position. It retains a new assignment revision and sends only coordination context. It neither replays human business commands nor changes the worker's model or directory. While that revision's brief and human input remain current, an execution guard allows only `read`, `read_image`, `glob`, `grep`, `present` and `coordinator_report`. Shell, downloads, generation, writing, delegation and tool transports are denied. A new direct human input restores ordinary capabilities as soon as it is consumed. The worker verifies existing work and reports against the new revision; further coordinated execution requires a separate authorized assignment. Busy input, live descendants or jobs, a mismatched `expected_worker_seq`, foreign ownership and conflicting request keys reject the operation; a busy rejection tells Main to wait for the next receipt instead of dispatching again. Exact retries reuse the recorded intent and receipt.

## Understand the implementation

The validated `muse_coordination` storage domain writes each task intent before creating its worker or sending input. Each request key is unique within its Main Session; exact retries return its existing task, while conflicting reuse is rejected. Every attempt retains its stable worker and message identities, source event and previous receipts. The current domain writes version 2 and reads compatible version 1 records; follow the [upgrade guide](../../../docs/upgrade-guide/v0.2.2-rc.2/muse-coordination-reconciliation/guide.md) before opening an existing profile or rolling back.

An assignment holds one of `maxWorkers` slots while it is reconciling, accepted, running, finishing or stopping; `needs-report` and `interrupted` wait for Main and hold none. A dispatch that creates a fresh worker starts only when it is the oldest waiting fresh-worker intent and a slot is free. Otherwise its recorded `dispatching` intent waits without a Session, and each time an assignment leaves the slot statuses the oldest waiting intent starts, ordered by task creation, so a fresh-worker revision of an older task starts before newer tasks. Dispatches to existing idle Sessions, including revisions and answers to `needs-input`, and reconciliations start at once and count toward the limit. Stopping a waiting task publishes `stopped` without creating a Session; a waiting task must be stopped before it can be revised or reconciled. A failed start publishes `interrupted` with the delivery error and tells Main to stop the task and dispatch it again rather than reconcile it.

In unattended mode, every write of an unresolved latest revision schedules a follow-up after the current coordinator operation; the follow-up re-reads the task, so repeated scheduling acts once. An `interrupted` revision whose worker is busy waits for the receipt published after quiescence, and one whose execution subtree cannot be verified is marked for attention instead of receiving a second worker in the same directory. A re-dispatch records a Host-authored revision with `redispatch.after`, a fresh worker identity, the previous directory and video selection, and the human and schedule inputs of earlier revisions; it adds no input of its own and starts under `maxWorkers` in task-creation order like any fresh-worker dispatch. A start failure publishes `interrupted` for the policy to resolve. Recovery schedules the same follow-up for every unresolved revision, including one published before `unattended` was enabled. A Main-authored dispatch or reconciliation resets the consecutive count, and an explicit stop is final. The coordinator writes an attention mark before Main's receipt, so the receipt carries it; `coordinator_tasks` rows include it, and the ledger keeps it for daily reporting. A worker report requires that no human message follows the assignment input, so a schedule reminder forwarded as that input is not human input.

One retained Main per profile serves scheduled runs indefinitely through the Host's automatic compaction, which shortens model context but not the Session log. The ledger keys tasks by Main Session: a new Main conversation would not list or stop earlier tasks, and their receipts would still wake the conversation that owns them. Main's routing never depends on its earlier context, because dispatch reads the latest owner input from the log, receipts are self-contained, and unattended follow-ups run in the coordinator.

Native inbox splices and admitted user messages establish delivery. Recovery checks those records before retrying a dispatch intent. A receipt without confirmed settlement becomes interrupted; generation is never automatically resubmitted. Opening Main preserves its task directory, so Main can reconcile, stop or revise the task. Each task recovers independently; a failure is logged and leaves that task's stored status unchanged. A waiting intent without a Session keeps waiting and starts after recovery within `maxWorkers`; one whose Session already exists is retried during recovery like any undelivered intent. Plugin unload drains its owned mutations and closes observers without cancelling ordinary execution Sessions.

The private `museCoordinationInput` Session projection retains only the latest consumed human identity and assignment brief identity for the reconciliation guard. It has no Client or wire view; the Session log and task ledger remain authoritative. Plugin unload releases the guard and projection registration together.

Worker settlement uses native Agent maintenance to retain newly queued input until the report write and notification finish. Input already consumed before settlement invalidates the earlier report; input arriving during settlement remains in the durable inbox for the next turn.

`coordinator_report` accepts only a consumed current assignment brief and its verified human input from the assigned worker. A reconciliation retains the existing human input identity and recorded log position; later direct input requires another reconciliation. Subsequent dispatch to another worker includes the verified human additions retained by earlier reconciliations. It captures successful native `present` declarations after that assignment's input and checkpoints the worker log. Its outcome is published only after the worker, its runtime descendants and their jobs settle, including pending creation and external execution cleanup. The runtime manager supplies tree ownership and nonblocking work checks; tree waits run outside the coordinator command queue so Stop remains available. A delegated failure after the report requires inspection and a new report. Idle without a report, while none of the assignment's brief or human inputs is still queued, becomes `needs-report`; after a reconciliation, its issue tells Main to inform the user instead of reconciling again. Text claiming completion alone does not complete the task. File declarations retain their source paths and are not copied or treated as content snapshots.

Stop persists `stopping`, removes unconsumed assigned input, cancels the assigned activity and its owned runtime descendants and jobs, and publishes `stopped` only after quiescence. Tree interruption includes pending startup and caller-delivered external execution, preserves child inboxes, and permits later task revisions to create new descendants. Only a busy worker that consumed a later human-authored message keeps running, and the task becomes interrupted; runtime continuations of the assignment, such as subagent settlement messages, are cancelled with it. A background producer that did not confirm resource release leaves the task interrupted until reconcile or Stop, and Stop then publishes `stopped` with that issue. This check covers only events after the current revision's input or recorded reconciliation position. Structured receipts wake Main through durable, identified native messages. UI status watches storage changes without model polling.

## Model Experience

### Routing and report tools

#### What the model sees

Main receives routing instructions plus `coordinator_sessions`, `coordinator_read`, `coordinator_view_image`, `coordinator_dispatch`, `coordinator_reconcile`, `coordinator_tasks`, `coordinator_stop`, `coordinator_show_report` and `coordinator_display_skill`. Where installed, `show_view` and `visualize` remain resident and excluded from Tool Search. Workers receive a logged `muse-coordination` assignment followed by the unchanged verified human messages, and use `coordinator_report` for an explicit outcome. `coordinator_read` reads a Session as a person opens it: `summary` (default) gives the latest input and reply excerpts; `outline` gives one line per turn with its input, tool counts, image count, failed results, end reason and reply, keeping the newest turns within `readChars`; `steps` pages compact task inputs, replies, tool calls, results with their image counts, and turn boundaries from a `from_seq` cursor, leaving runtime context out; `events` pages raw history. `outline`, `steps` and `coordinator_view_image` also read subagent Sessions, while `events` stays limited to ordinary Sessions. `coordinator_view_image` returns one stored image by event sequence and zero-based index, so Main can look at a frame on demand; status digests and the other views never carry images. Task lists and routing results are bounded task rows that count presented files, and receipt summaries are bounded by `summaryChars`. Reports distinguish waiting to start, preparing reconciliation, delivered, running, finishing, interrupted, stopped and worker-reported completion. In unattended mode, Main's tool list omits `humanTools`, receipts tell Main to record outcomes without asking and carry any `attention`, task rows include `attention` when set, and the worker brief replaces the question guidance with unattended guidance.

#### Token effect

History enters only when requested. Task lists and dispatch, reconcile and stop results add one row per task instead of every revision. Dispatch repeats the original task material and revision requirements in the chosen worker; terminal receipts add one bounded account to Main. Reconciliation adds a coordination-only verification request to the retained worker without duplicating its human messages. Report cards append the selected bounded receipt as ordinary logged tool output. The task watch does not call a model. An automatic re-dispatch repeats the original task material in a fresh worker, and Main receives one receipt per terminal revision.

#### KV Cache effect

Stable policies and prior messages remain unchanged; new dispatches, reads and receipts append normal logged input or tool results.

## Known Limitations and Deferred Work

- A worker report is evidence of its account and native file declarations, not independent creative or human acceptance. Paid-generation authorization remains with the execution workflow.
- Coordination is process-local within one owner's profile. Cross-device workers and multi-owner shared task directories are not supported.
- Without `unattended`, ambiguous restart settlements require inspection and an explicit continuation, and no automatic paid retry is inferred from a missing report. With it, a fresh worker repeats the task in the same directory up to `redispatchLimit` times, so worker steps such as paid generation or uploads must tolerate a repeat; an app restart interrupts every running assignment.
- `maxWorkers` counts coordinator assignments only. Subagents, Team tasks and jobs inside a worker, and direct human work in a worker chat, have their own bounds or none; `maxActiveSubagents` bounds subagents per worker tree but not jobs. At that limit a subagent start is rejected rather than queued. Dispatches to existing idle Sessions and reconciliations start at once, so the executing count can exceed `maxWorkers`. A long-running assignment holds its slot until it settles or is stopped. A waiting fresh worker takes Main's dialogue-model selection when it starts, not when it was dispatched.
- Without `taskRoot`, fresh workers use Main's directory unless Main passes `cwd`, because tasks on one short-drama project share its folder. Main's prompt routes a change to drafts an unfinished task is editing as that task's revision; the coordinator does not detect two workers writing the same files. `taskRoot` folders are never removed.
- Without `unattended`, routing worker questions to Main is guidance, not enforcement: content-listening acceptance and budget approval verify answers to `ask_user_question` in the worker Session, so those questions appear in the worker chat. With it, those approvals cannot be given and the task ends blocked or needs attention.
- In unattended mode, any Session that can create a schedule targeting Main, including a worker with schedule tools, can trigger dispatch. A forwarded reminder carries schedule attribution rather than human authority.
- Main's log and the ledger grow without pruning. Every Main tool call and dispatch reads Main's complete log, so routing latency grows with the number of scheduled runs.
- Dispatch forwards only Main human messages, one per revision. Requirements spread across earlier Main messages and answers given through Main's question or form cards reach a worker only when the user sends them as a message; a revision without a new Main message forwards the previous message again.
- Receipt file lists are not bounded; only the summary is.
