# @deepseek-ai/dsh-session-coordinator

[English](README.md) | 中文

<a id="summary"></a>
## 概述

桌面端直接在本机默认工作间打开当前账号的主会话。主会话处于空闲且尚未收到用户消息时，可根据已核实的身份主动问候一次。派发任务时记下用户已确认的云项目；主会话以后切换项目时，已派任务继续使用原项目。

将此可选 Host 插件与只负责调度的预设组合。主会话搜索当前用户配置中的普通会话、查看候选会话摘要，自主决定复用空闲会话还是新建执行会话。执行会话保留普通工具、历史和预设。独立任务账本保存派发与执行修订；送达回执不代表完成或用户验收。

## 使用此包

在 Host 加载默认导出，将 `/worker` 与普通工具共同加载；仅在指定主会话预设内组合 `/main`。Muse 提供 `main-session`，默认仍为 `short-drama`。可选[主会话导航插件](../../client/ui-session-coordinator/README.zh.md)提供固定主会话入口和启动导航。执行会话保留原生侧栏行，结果通过主会话聊天消息返回。移除 Host 插件仍保留账本文件与普通会话历史。

`mainPreset` 与 `workerPreset` 指定不同角色；`searchLimit` 限制搜索条数，`readChars` 限制每页原始历史字符数，但单个超限事件完整返回。`noteChars` 限制主会话写的每条路由说明（`instructions`、`reason`），`summaryChars` 限制执行会话汇报摘要。`maxWorkers`（默认 3）限制同时执行的协调任务数，超出时需要新建执行会话的派发会等待。检索权限限于当前本地配置的所有者，可跨工作目录，不会打开其他远程账号或授权读取其他用户配置。Remote 方法要求全局所有者权限，访客的局部授权不能访问任务目录。

Host 同时挂载 [`dsh-session-activity`](../session-activity/README.zh.md) 时，`coordinator_sessions` 的每一行增加与会话栏一致的 `status` 状态行（运行中、空闲、在等回答或审批、上一轮失败，以及最近用的工具和还在跑的作业、子代理），协调器还会关注每个占用 `maxWorkers` 名额的任务的执行会话，任务离开这些状态或进展服务被替换时释放关注。主会话因此在回执之间收到状态摘要：变化等主会话下一步时带入，执行会话等待输入、轮次失败或停滞会唤醒主会话。此时主会话提示词会说明：摘要不需要回复，也不需要因此轮询，细节用 `coordinator_read` 查看；有人值守时请用户到等待中的执行会话处理；无人值守时只记下需处理事项并等回执。未挂载该插件时各行没有状态，主会话只收到回执，提示词不变。

无人回答问题的部署（例如每日定时运行）设置 `unattended`。此时主会话除用户消息外还能按最新一条定时提醒派发，主会话和已分配执行会话的整棵执行树都不能调用 `humanTools`，默认是 `ask_user_question` 和 `exit_plan_mode`。任务最新修订以 `needs-report`、`failed`、`blocked` 或 `needs-input` 结束，或者执行会话静止后停在 `interrupted` 时，协调器把它重派给同一目录中的新执行会话。连续自动重派达到 `redispatchLimit`（默认 1）次后，改为在该修订上记录 `attention` 原因和时间。`taskRoot` 是一个绝对目录，为每个任务提供独立文件夹 `<taskRoot>/<任务标识>`：派发在该任务第一个新执行会话启动前创建它，并拒绝其他 `cwd` 或复用其他目录中的会话。用 subagent 插件的 `maxActiveSubagents`（默认 8）限制每个执行会话内的子代理：每个执行会话是自己子代理树的根，因此 `maxWorkers` 个新建执行会话任务同时最多运行 `maxWorkers` × `maxActiveSubagents` 个子代理。该设置适用于 Host 上所有根会话。

主会话的正向工具清单允许协调工具、`ask_user_question`、`show_view` 与 `visualize`。固定入口 `coordinator_display_skill` 仅通过原生注册表读取允许模型调用的 `visualize` Skill；通用 `skill`、文件与 shell 工具仍不可用。执行守卫同时拒绝其他工具，包括后注册工具与 PTC 传输。执行会话通过普通会话控制器独立创建，不继承主会话的限制。主会话负责路由请求、转告回执和执行会话的问题、处理停止请求；规划、调研、写稿、文件修改、下载、生成和复核仍交给执行会话。任务说明和 `coordinator_report` 引导执行会话以 `needs-input` 汇报并把一个问题写在摘要中，而不是在自己的聊天中提问，由主会话转告用户。执行会话仍保留 `ask_user_question`，因为短剧的内容试听验收和预算授权只认同一会话中提问得到的回答。

主会话系统提示词将其限定为路由：不复述或补充要求，核对前不读取执行会话历史，派发后结束本轮而不轮询。要求分散在前面几条消息里时，请用户用一条消息说完整；`needs-input` 问题用文字而不是卡片转告，用户回复后再派发修订；核对后仍没有汇报的任务不再自动核对。提示词说明新建执行会话的派发返回 `dispatching` 表示正在排队、有空位会自动开始，主会话应告知用户而不是再次派发；还说明新执行会话与主会话共用目录，`cwd` 只填另一个文件夹而不是项目子目录，要改的稿件正由某个未结束的任务在改时作为该任务的修订路由。提示词优先要求聊天展示清晰易读：简短结论、信息分组，以及派发后和任务结束时展示任务汇报卡片。提示词引导模型用结构化卡片展示对比、清单、选择和表单，简短问答保留文字。这属于模型指导；任务通知不会在未调用展示工具时自行创建卡片。 设置 `unattended` 时，提示词改为说明没有人回答、请求可以来自定时提醒、消息列出的每个独立对象各派一个任务，以及未解决的任务由协调器处理，主会话只记录回执、不提问。设置 `taskRoot` 时，提示词说明每个任务在自己的文件夹执行，只复用同一任务的执行会话。

有长度上限的路由说明标记为转交上下文，任务说明将其标为说明而非要求。只有 Host 核对过的原始用户消息保留原用户来源与不变正文，调度者补写的说明不会成为用户授权。派发原样携带主会话最新一条用户消息与附件、此前每次修订记录的消息和路由说明。新执行会话继承主会话的对话模型选择，复用会话保留原对话模型。`inheritJubianVideoSelection` 默认开启，派发时记录主会话当前的剧变视频模型（如已选择）。Muse 桌面关闭此项。新任务不带视频模型标识，同一任务的后续修订沿用此前记录的标识。执行会话收到输入前，必须通过剧变选择服务应用任务原有的标识；服务或选项不可用时，派发会报错。

复用会话必须空闲，没有待处理输入、活跃作业或未结算协调任务。归档会话和子代理只能用作参考。无法复用时，由 Agent 选择其他执行会话。派发修订需要预期修订号，且上一轮已经结算或被明确停止，不会覆盖正在执行的任务。用户直接在被占用的执行会话中追加输入时，会使原报告失效并通知主会话，不会取消用户的新工作。

`coordinator_show_report` 将已核实所有者的任务标识、当前修订、执行会话、状态和原生文件声明保存在带版本的工具结果 metadata 中。省略或传空标识列表时先选未结算任务，再选最近任务；`searchLimit` 同时限制汇报条数，并明确返回总数与截断标记。`coordinator_tasks` 按同样顺序返回路由任务行但不展示卡片。每行只统计交付文件数量而不列出文件；整个列表的序列化字符数受 `readChars` 限制，放不下的任务行会被省略并设置 `truncated`。派发、核对和停止只返回最新修订的一行路由任务。汇报卡片的模型结果与 metadata 合计序列化字符数受 `readChars` 限制，只保留完整任务回执；首个任务自身超限时明确失败，不截断摘要或文件。不存在、外部所有者、重复或超限的标识会失败。模型不能填写完成状态、进度百分比或产物路径。Client 在聊天内展示卡片，并通过现有任务监听跟进被捕获的同一修订；后续修订不会替换旧回执。

“新会话”下方的 Muse 小蜘蛛入口打开默认工作间中固定的主会话。创建过程使用原生工作区与会话控制器，重复点击或重新启用插件会复用同一会话。执行会话保留各自选定的项目目录。

`coordinator_reconcile` 请求核对空闲原执行会话中的工作，主会话无需先读取其历史。它检查预期任务修订，记录执行会话当前日志位置；可选的 `expected_worker_seq` 与该位置不同时拒绝。它保存新修订，仅发送协调上下文，不重放用户业务命令，也不改变执行会话的模型或目录。当本轮任务说明与用户输入仍是当前输入时，执行守卫只允许 `read`、`read_image`、`glob`、`grep`、`present` 和 `coordinator_report`，拒绝 shell、下载、生成、写入、委派和工具传输。新的直接用户输入一经消费即恢复普通能力。执行会话核对既有工作并按新修订汇报；后续协调业务执行需要另外派发已授权任务。有待处理输入、活跃后代或作业、`expected_worker_seq` 不符、所有者不符或请求 key 冲突时拒绝操作；因忙碌被拒时，错误提示主会话等待下一条回执，不要重新派发。相同请求重试复用已有意图与回执。

<a id="understand-the-implementation"></a>
## 实现说明

经校验的 `muse_coordination` 存储域在创建会话或发送消息前持久化任务意图。同一主会话内请求 key 唯一；完全相同的重试返回已有任务，冲突复用会被拒绝。每轮保留固定执行会话和消息标识、原始事件位置及此前回执。当前存储域写入版本 2，同时兼容读取版本 1；打开既有配置或回滚前，遵循[升级指南](../../../docs/upgrade-guide/v0.2.2-rc.2/muse-coordination-reconciliation/guide.zh.md)。

任务在核对中、已送达、执行中、收尾或停止中时占用一个 `maxWorkers` 名额；`needs-report` 和 `interrupted` 等待主会话处理，不占名额。需要新建执行会话的派发只有在它是最早等待的新建意图且有空闲名额时才开始；否则已记录的 `dispatching` 意图在没有会话的情况下等待。每当有任务离开占用名额的状态，就按任务创建顺序开始最早的等待意图，因此较早任务的新建执行会话修订先于较新的任务开始。派发到既有空闲会话（包括修订和对 `needs-input` 的回答）以及核对会立即开始，并计入名额。停止等待中的任务会直接发布 `stopped`，不创建会话；等待中的任务须先停止才能修订或核对。开始失败时发布带送达错误说明的 `interrupted`，并告诉主会话先停止该任务再重新派发，而不是核对。

无人值守模式下，每次写入未解决的最新修订，都会在当前协调操作之后安排一次后续处理；后续处理重新读取任务，因此重复安排只生效一次。执行会话仍忙的 `interrupted` 修订等待静止后发布的回执；执行子树无法核实时标记待处理，而不在同一目录再派一个执行会话。重派记录一个由 Host 创建的修订，带 `redispatch.after`、新的执行会话标识、原目录和视频选择，以及之前各修订的用户输入和定时提醒；它不添加自己的输入，像其他新建执行会话的派发一样受 `maxWorkers` 约束、按任务创建顺序启动。启动失败会发布 `interrupted`，再交给该策略处理。恢复时也会为每个未解决的修订安排同样的后续处理，包括启用 `unattended` 之前发布的修订。主会话发起的派发或核对会重置连续计数，明确停止则不再处理。协调器在主会话收到回执前写入待处理标记，因此回执带有该标记；`coordinator_tasks` 的任务行包含它，任务账本保留它供每日汇总。执行会话汇报要求任务输入之后没有用户消息，因此作为任务输入转发的定时提醒不算用户输入。

每个配置保留一个主会话，依靠 Host 的自动压缩长期处理定时运行；压缩缩短模型上下文，不缩短会话日志。任务账本按主会话标识归属任务：新的主会话对话看不到也停不了之前的任务，这些任务的回执仍会唤醒所属的对话。主会话的路由不依赖之前的上下文：派发从日志读取最新的所有者输入，回执自带完整信息，无人值守的后续处理由协调器执行。

原生收件箱变更与已接收用户消息证明送达。恢复时先核对这些记录，再决定是否补发尚未送达的派发意图。有送达记录但无法确认结算时标记中断，不会自动重新提交生成。打开主会话仍能查看任务目录，主会话可以核对、停止或修订任务。每个任务独立恢复；某个任务恢复失败时记录日志，并保留其已存状态。尚无会话的等待意图继续等待，恢复完成后在 `maxWorkers` 范围内开始；执行会话已存在的意图与其他未送达意图一样在恢复时补发。卸载插件会等待自身写入完成、关闭观察流，不会取消普通执行会话。

私有 `museCoordinationInput` 会话投影只保留最新已消费用户输入标识和任务说明标识，供核对守卫使用；不提供 Client 或 wire 视图，会话日志和任务账本仍是事实来源。卸载插件会同时释放守卫和投影注册。

执行会话结算使用原生 Agent 维护任务，在报告写入和通知完成前保留新排队输入。结算前已经消费的新输入会使旧报告失效；结算期间到达的输入保留在持久收件箱中，供下一轮处理。

`coordinator_report` 只接收指定执行会话已经消费的当前修订说明与核实过的用户输入。核对操作保留原用户输入标识和已记录日志位置；后续直接输入需要再次核对。之后派发到其他执行会话时，会带上此前核对保留的已核实用户补充。该工具收集任务输入之后成功的原生 `present` 声明并刷盘。执行会话、其运行时后代和作业全部结束后才发布结果，包括待创建工作与外部执行清理。运行时管理器提供子树归属和非阻塞工作检查；等待子树在协调器命令队列外进行，因此停止操作仍可执行。汇报之后出现的委派执行失败需要核对并重新汇报。空闲且没有汇报、任务说明和用户输入也都不在队列中时，标记 `needs-report`；核对之后出现这种情况时，问题说明提示主会话告知用户而不是再次核对。仅文字声称完成不会完成任务。文件保留实际来源路径，不复制文件，也不将声明视为文件内容快照。

停止操作先保存 `stopping`，移除未消费任务输入，取消任务活动、其运行时子代理和作业；确实静止后才发布 `stopped`。子树中断包括待创建工作和向调用方交付的外部执行，保留子级收件箱，并允许后续任务修订创建新的后代。只有忙碌且已消费后续用户消息的执行会话会继续运行，任务标记为中断；属于该任务的运行时续接消息（例如子代理结束通知）随任务一起取消。后台生产者未确认释放资源时，任务保持中断，直到核对或停止；停止后发布带该问题说明的 `stopped`。此检查只看当前修订的输入或已记录核对位置之后的事件。结构化回执通过有固定标识的原生持久消息唤醒主会话。界面监听账本变化，不消耗模型轮询。

## 模型体验

<a id="routing-and-report-tools"></a>
### 调度与汇报工具

<a id="what-the-model-sees"></a>
#### 模型可见内容

主会话获得调度说明及 `coordinator_sessions`、`coordinator_read`、`coordinator_view_image`、`coordinator_jobs`、`coordinator_settings`、`coordinator_dispatch`、`coordinator_reconcile`、`coordinator_tasks`、`coordinator_stop`、`coordinator_show_report` 和 `coordinator_display_skill`。已安装的 `show_view` 与 `visualize` 保持常驻且排除于 Tool Search。执行会话先接收写入日志的 `muse-coordination` 任务说明，再接收保留原文的已核实用户消息，用 `coordinator_report` 明确汇报结果。`coordinator_read` 像人打开会话一样读取：`summary`（默认）给出最近的输入和回复片段；`outline` 每轮一行，写明输入、工具计数、图片数、失败结果、结束原因和回复，在 `readChars` 内保留最新的轮次；`steps` 从 `from_seq` 游标开始分页列出精简的任务输入、回复、工具调用、附带图片数的结果和轮次边界，不含运行时上下文；`search` 列出该会话中匹配全文 `query` 的事件及其序号和片段，最多 `searchLimit` 条且受 `readChars` 限制；部署关闭了全文索引时（例如 Muse 桌面版），改为在该会话的精简步骤中逐条查找该文本；`events` 分页返回原始历史。`outline`、`steps` 和 `coordinator_view_image` 也能读取子代理会话，`events` 仍只限普通会话。`coordinator_view_image` 按事件序号和从 0 开始的序号返回一张已存储的图片，让主会话按需查看某一帧；状态摘要和其他视图都不带图片。`coordinator_jobs` 列出某个会话的后台作业及其状态、进度、标签和输出大小，或从某个字节位置读取一个作业的输出（默认读最后 `readChars` 字节），不会消耗该会话自己尚未读取的输出。`coordinator_settings` 读取生效的设置，密钥已打码；放得下 `readChars` 时返回全部命名空间，否则只返回命名空间名称。这三项都是只读的。任务列表和路由结果是统计交付文件数量的有界任务行，回执摘要受 `summaryChars` 限制；回执区分等待开始、准备核对、送达、执行、收尾、中断、停止和执行会话报告完成。 无人值守模式下，主会话的工具列表不含 `humanTools`，回执要求主会话只记录结果、不提问，并带上已有的 `attention`；任务行在有标记时包含 `attention`；执行会话的任务说明用无人值守说明替换提问指引。

<a id="token-effect"></a>
#### Token 影响

历史仅按需读取。任务列表以及派发、核对和停止结果每个任务只追加一行，不含全部修订。派发会在选定执行会话中包含原始任务材料及修订要求；终态回执向主会话追加一次结果说明。核对操作只向原执行会话追加协调核对请求，不重复用户消息。汇报卡片将所选的有界回执作为普通的已记录工具输出追加。任务观察流不调用模型。 自动重派会在新执行会话中重复原始任务材料，主会话每个结束的修订收到一条回执。

<a id="kv-cache-effect"></a>
#### KV Cache 影响

稳定策略与已有消息不变，新派发、读取和回执作为普通日志输入或工具结果追加。

<a id="known-limitations-and-deferred-work"></a>
## 已知限制与延后工作

- 执行会话汇报只能证明其说明和原生文件声明，不等于独立创作审查或用户验收；付费授权仍由执行流程负责。
- 协调范围为单进程、单个所有者配置，不支持跨设备执行或多人共享任务目录。
- 未设置 `unattended` 时，重启后结算不明的任务需要检查并明确续做，不会因缺少报告自动重试付费操作。设置后，新执行会话会在同一目录最多重做 `redispatchLimit` 次，因此付费生成、上传等步骤必须能承受重复；应用重启会中断所有执行中的任务。
- `maxWorkers` 只统计协调任务。执行会话内的子代理、Team 任务和作业，以及用户在执行会话聊天中直接发起的工作，有各自的上限或没有上限；`maxActiveSubagents` 限制每棵执行树的子代理，不限制作业。达到该上限时启动子代理会被拒绝，而不是排队。派发到既有空闲会话和核对会立即开始，因此同时执行的数量可能超过 `maxWorkers`。长时间运行的任务在结算或停止前一直占用名额。等待中的新执行会话在开始时才继承主会话的对话模型选择，而不是在派发时。
- 未设置 `taskRoot` 时，新执行会话在未传 `cwd` 时使用主会话目录，因为同一短剧项目的任务共用其文件夹。主会话提示词把对未结束任务正在修改的稿件的改动作为该任务的修订路由；协调器不检测两个执行会话写同一文件。`taskRoot` 下的文件夹不会被删除。
- 未设置 `unattended` 时，执行会话的问题交给主会话转告只是引导，不是强制：内容试听验收和预算授权只认执行会话中 `ask_user_question` 的回答，因此这些问题会出现在执行会话聊天中。设置后无法给出这些授权，任务以受阻结束或标记待处理。
- 无人值守模式下，任何能创建以主会话为目标的定时任务的会话（包括带定时工具的执行会话）都能触发派发。转发的提醒带定时来源，不代表用户授权。
- 主会话日志和任务账本只增不删。主会话每次调用工具和派发都读取完整日志，因此路由延迟随定时运行次数增长。
- 派发只转发主会话的用户消息，每次修订一条。分散在主会话更早消息中的要求，以及通过主会话提问或表单卡片给出的回答，只有用户以消息发出后才会到达执行会话；没有新主会话消息的修订会再次转发上一条消息。
- 回执中的文件列表没有上限，只有摘要受限。
