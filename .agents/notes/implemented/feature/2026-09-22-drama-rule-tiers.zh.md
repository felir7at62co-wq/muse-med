# Agent Note: Drama rules sit in one of three tiers

Status: implemented

[English](2026-09-22-drama-rule-tiers.md) | 中文

## Problem

仿真人短剧流水线的规则散落在预设正文、技能正文和三个执行点上，而且没有任何地方规定「一条新规则该放哪一层」。同一批数字——单镜 1–4 秒、9 个有效字/秒、36 字、15 字拆句——既以「硬门禁」的措辞出现，又以建议的措辞出现，模型因此分不清哪条必须满足、哪个数字可以商量。一个确实需要更紧节奏上限的项目（例如本产品自己「每镜不超过 18 个有效字」的交付要求）无处声明它：它只是提示词里的一句话，忽略它的成片没有任何东西会拒绝。

## Decision

每条规则只属于一层，层级决定它的归属方：

1. **执行底线——由操作本身拒绝。** 在每个项目都成立：短剧门禁的 idempotency_key、镜头脚本与 matched JSON 的结构、付费分镜提交前的正式资产、新建计费资产前的对账、以及「操作绑定到具体项目」；付费调用前的剧变账本与预算门禁；以及 `drama_shot` 的结构硬失败与打包预算。
2. **项目交付要求——项目声明，工具判定。** 项目在标记项目根的 `project_config.json` 里声明自己的要求，`drama_shot` 读取它并按它判定：`delivery.max_effective_chars_per_shot` 是每镜有效字上限，超过它判失败（`speech_exceeds_project_limit`），而不是警告。每个方法都会解析项目——先用自己的 `project` 参数，否则从脚本所在目录向上找最近的 `project_config.json`（四层以内）——所以 `validate` 与 `preview` 在编译之前就能报告这条要求。拒绝文案同时给出两条正当修法：按原文语义拆句，或改掉该项目的这条要求。项目没声明上限时，内建数字仍然只是建议；声明的值存在但不是正整数时，本次调用直接失败，而不是被忽略。
3. **创作建议——仅提示。** 单镜 1–4 秒、9 个有效字/秒、36 字建议、15 字拆句阈值、优先画面内对白，都只是警告或正文提示，从不阻塞编译；模型可以因表演、停顿或叙事需要偏离，但要保留原文、原文顺序与说话人。

短剧预设把这三层讲给模型，使每次拒绝都能被归层；仓库这一侧的工作是让「项目层」真的可判定，而不只是描述。

## Alternatives considered

**项目声明了上限也只做建议。** 那样项目要求就与本工具自己的建议无从区分，而这正是分层要消除的混淆。保留的出路是显式的：改这条要求就是在改该项目自己的配置。

**把每镜上限放进部署级的 `drama` 设置段。** `drama-settings` 拥有的是整份部署共用的文档，按项目不同的要求放不进去。复用项目配置，是因为流水线本来就写它，短剧门禁也本来就按其中的 `jubian_script_id` 绑定付费操作。

**只从显式的 `project` 参数读取这条要求。** 那样 `validate` 与 `preview` 都读不到，模型要等编译已经失败才知道项目的这条要求。向上查找与 `video_bans.py` 用同一个文件、同样的方式解析项目根。

**把项目上限降级为警告，再加一个报告字段。** 那需要往工具固定的输出 schema 里加字段，而模型仍然可以无视它；把文件、键与值一起写进拒绝文案，是更小也更强的接口。

## Consequences

超过项目声明上限的台词现在会阻塞编译且不写任何文件；而同一个脚本放进一个没有声明上限的项目，仍然只带警告通过。于是分层不只写在正文里，也体现在 `drama_shot` 自己的结果里。

该键在包 README 的两种语言里都有说明，写进了工具描述（让拒绝能直接连到 `project_config.json`），也进入了生成的工具目录。

无法解析的项目配置等于没有要求，内建数字继续只作建议；同一个坏文件也会让短剧门禁无法把付费调用绑定到该项目。两者并不矛盾：要求是可选的，绑定不是。

第三层的规则刻意不进工具：强制节奏会逼流水线改写用户写下的原文，而格式规则存在的意义正是避免这件事。
