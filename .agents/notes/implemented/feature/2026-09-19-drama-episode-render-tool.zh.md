# Agent Note: Short-drama episode rendering as a tool

Status: implemented

[English](2026-09-19-drama-episode-render-tool.md) | 中文

## Problem

短剧流水线的交付样式——1440x2560@60、24M 目标码率与 30M 上限、SimHei 68 字幕加右下角唯一的 `内容由AI生成` 标记、用最后一镜真实尾帧定格的 2 秒片尾，以及以 `alimiter=0.95` 收尾的三路混音——原本写在 `tweet-drama-background-render` 技能里，由技能让模型启动的一个 Python 脚本执行。跳过技能、或用错参数启动脚本的会话仍然能交付点什么：样式只是建议，唯一的执行者是事后看片的人。

有三件事说明那不是它该待的地方。样式是可判定的——分辨率、帧率、码率下限、字幕几何、片尾长度、音频增益都能在成片上实测——所以能检查的规则就该在写文件的地方检查。其中两步是静默失败而不是响亮失败：`-sseof -0.05` 在部分片子上不写尾帧却返回 0；GPU 编码器探测失败与探测成功看起来一模一样，除非把原因带出这次调用。而当时的结果是一段打印出来的 JSON，而不是会话能据以行动的值。

## Decision

[制作策略与结果证据决策](2026-09-21-drama-policy-and-result-evidence.zh.md) 扩展了素材选择、缓存身份与审核报告。本文保留交付样式、尾帧与工具归属决策。

`drama/` 组的第二个包 `@deepseek-ai/dsh-tool-episode-render` 注册一个模型可见的工具 `drama_render`，含三个方法。

`prepare` 在不编码画面的前提下构建渲染器要读的目录布局：每个源成片复制到 `video/<集>/shot_00N.mp4`，时间线按 **ffprobe 实测**时长（而不是声明时长）铺进 `editing/<集>-timeline.json`，整集原声在 `audio/<集>.wav` 里按每镜各自的起点放置它自己的声音拼成（不加增益、不逐镜重采样），字幕装到 `editing/<集>.srt`。结束时刻超过整集画面的 cue 作为警告报出。

`render` 按运营确认过的样式出片并返回实测参数：分辨率、帧率、码率、时长、大小与编码器。正片镜头按各自的时间线时长重编并逐集缓存；片尾用最后一镜经过证明的尾帧重建；正片与片尾用流拷贝拼接；ASS 脚本烧录进画面；三路音频混音后带 faststart 索引封装。

`verify` 按时间线与字幕检查成片：总时长、流、帧率、总码率下限、黑场、静音，以及是否存在会被烧到画面之外的字幕 cue。

让渲染无法进行的问题——缺参数、缺输入、命令失败、尾帧无法证明——都会抛错并给中文修法。成片自身的问题不抛错：它作为检查项回来，`ok: false`，每个失败检查一行修法，因为运营仍需要这个文件和这份测量。面对坏文件，`verify` 从不抛错。

交付样式不可配置。画面几何、帧率、码率控制、字幕样式、片尾长度、特效速度与限幅器都是 `src/delivery.ts` 里的常量，因为它们是运营确认过的规格，而不是逐部署的选择。`Config` 暴露的是真正会变的东西：ffmpeg 与 ffprobe 可执行文件、运营确认过的两个音频增益、是否探测 GPU 编码器，以及 libass 到哪里找字幕字体。

## 两个坑

**尾帧是被证明的，不是被假设的。** 抽帧窗口是 `-sseof -0.1`，因为 `-sseof -0.05` 在部分片子上不写文件却返回 0——其中包括一个 13.041667 秒的去字幕件——于是片尾定格在一张错误的帧上，日志里没有任何痕迹。只把窗口放宽还不够：抽帧之后，这一帧的 `framemd5` 会与该源顺序解码的最后一帧比对。两者不一致时按帧号重抽；仍不一致就停止渲染，绝不定格一张未经验证的帧。比对的三个哈希与两个布尔值在 `tail_frame` 里返回，所以会话能看到定格了什么、为什么。

**编码器回退是被记录的。** 探针编码一帧 `color=black:s=256x256:d=0.1` 的源；尺寸很重要，因为部分 NVIDIA 代次会拒绝更小的帧（低于 NVENC 的最小尺寸），那会把一块能用的卡报成不可用。驱动过旧、缺少 NVENC 构建、GPU 被占用，三种情况失败表现一致，而交付必须照常进行，所以失败按设计回退 `libx264`——同时把探针自身输出压成一行写进 `encoder_fallback_reason` 与渲染日志。`preferNvenc: false` 会跳过探测并改记这个原因。

## Alternatives considered

**保留 Python 渲染器并包一层。** 一个转而调用 `render_episode.py` 的工具能保住一份实现、立刻上线。它也会让交付样式无法在本仓库里被表达：样式仍然是本仓库并不拥有的那个文件里的 argparse 默认值，两个坑仍然没有记录，而结果仍然是打印出来的 blob，而不是按 schema 校验过的值。

**只移植 render 方法。** `prepare` 正是这条流水线自己的布局决策所在——时间线用哪些时长、每镜的声音从哪一刻开始、缺音轨意味着什么。把它留在另一份手写脚本里，会让同一个时钟分裂到两份实现上，而这正是这次移植必须复现的那次重剪所暴露的漂移。

**把交付样式做成可配置。** 每个值都可以做成 `Config` 字段。它们没有，因为字段是一种承诺：承诺改变它会被支持。1080x1920 的交付、12M 的码率、或另一种字幕字体，在这里不是部署选择，而是另一种运营尚未批准的交付。暴露出来的四个字段，正是运营已经在用的变化。

**把成片缺陷作为错误返回。** 低于码率下限的渲染可以抛错而不是返回 `ok: false`。它没有，因为那时文件已经存在：拒绝报告会浪费这次渲染，并藏起运营判断是否重编所需的测量。

**照 Python 渲染器写 `exports/render_tasks.json` 状态文件。** Python 把每次渲染的结果追加进一个项目状态文件。本包改写成逐集的渲染日志，并返回同样的事实：这条流水线的唯一状态文件是 `pipeline_state.json`，再由一个工具写第二份，会跟它争夺权威。

## Consequences

交付样式现在有了一个可执行的家，两个静默失败也有了被记录的地方。从不读技能的会话，仍然无法在结果不说明的情况下交付规格之外的成片，而且它能从一次调用里读到全部缺陷。

代价是过渡期的第二份实现。在会话迁移过去之前 `render_episode.py` 仍是生产路径，所以样式会并存一段时间；Python 仍是运营已经批准过的字节布局的参照物，而本包的 Dev Note 列出了移植刻意不同的五处。`tweet-drama-background-render` 技能未被改动。

三条限制是刻意的，并记录在包 README 里：片尾每次渲染都重建而不复用缓存，因为缓存里的片尾可能早于一次重剪，而这一步的意义正是证明；`render` 不是事务，所以中断的运行可能留下半个 `base.mp4`，下一次运行会覆盖它而不是校验它；混音不做电平表，所以 `alimiter=0.95` 是唯一的天花板，比被替换的 master 更响的素材仍可能在它之前就削顶。

本包在调用之间不保留状态，也不发布不变式伴随包：每个答案都是它所读文件与所启进程的函数，没有独立变化、可供检查的观测。

## Testing

`packages/drama/tool-episode-render/tests/` 让每个模块都由自己的规格覆盖：进程边界对着一个真实启动的 Node 进程测，它之上的全部则对着一个桩通道测——该通道应答 ffprobe 报告、`framemd5` 行与抽尾帧的 seek。`npx vitest run packages/drama/tool-episode-render --coverage` 在十二个源模块上报告逐文件 100% 的语句、分支、函数与行覆盖。工具规格挂载插件，并把每个返回值按该工具自己的 `output.schema` 校验，所以与声明 schema 漂移的规范值会让测试失败，而不是让会话失败。尾帧证明由它存在的那三种情况钉住：抽到的帧与顺序解码一致、不一致因而按帧号重抽、以及根本无法证明。
