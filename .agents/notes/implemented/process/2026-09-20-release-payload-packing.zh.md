# Agent Note：发布包的打包

Status: implemented

[English](2026-09-20-release-payload-packing.md) | 中文

## 问题

产品以一个 Windows 安装器交付：它下载预构建的压缩包、校验、解包，从不在用户机器上跑构建或包管理器。这个约定决定了安装器开工之前必须先有什么：7 个 `.tar.zst` 包，外加一份 `manifest.json`，其中记录每个包的字节数、sha256 与解包目录。此前没有任何东西产出它们。

产出它们不是普通递归打包。产品运行所依赖的这些目录是本机的，且带 NTFS junction：`profiles/web/node_modules` 指向工作区、一个 vendor 树与一个 npm 缓存，而 `packages/*/node_modules` 指回同级源码，因此朴素的遍历要么把链接本身装进包里，要么顺着这个环走到文件系统深度上限。包还必须瘦身——Python 树里有 742 MB 的 `*.lib` 与 113 MB 的 source map，运行时一个都不加载——而瘦身不得动开发者的目录，因为产品的开发就在同一批目录里进行。

一个文件也不许同时进两个包，而安装器依赖的校验必须能仅凭压缩包本身复现，而不是靠它们来源的目录。

## 决策

`scripts/release/pack-release.ts` 由 `tsx` 直接运行，三种模式；`scripts/release/tar-zstd.ts` 负责写归档。没有新增依赖：仓库里的 `tar` 是 `apps/desktop` 的传递依赖，从 `scripts/` 无法解析，因此归档用 Node 24 自带的 `zlib.createZstdCompress` 加一个极小的 ustar 写入器产出。

`--plan-only` 每个包打印一行——包名、来源、文件数、原始字节、各排除规则省下的字节、`unpackTo`——并且什么都不写。`--build --out <目录> [--only <子串>]` 写出选中的包与 manifest，并与已有 manifest 合并，使单个包可以单独重跑；`--only` 的存在是因为 Python 包有 2.7 GB 输入。`--verify <目录>` 重新读盘上每个包，重算字节数与 sha256，与 manifest 对照，并断言包内不含排除规则禁止的内容。

**junction 与符号链接一律跟读，绝不装入链接本身。** 每次遍历先 `lstat`，遇到链接就用目标的 `stat` 替换，于是成员保存的是目标字节、用的是链接自己的名字。此外每个目录都把 `realpath` 记进本包的去重集合：一个目录被到达两次，要么是链接环，要么是同一子树换了个名字，两者都已被打包，访问一次就够。正是这一点把 profile 的 junction 农场变成真实文件而没有递归到 `ELOOP`，也顺带合并了技能树里共享子树的重复副本。

**瘦身是打包期过滤。** 有序规则各自带标签与判定函数；目录规则在读取子树之前剪枝，文件规则把被跳过的文件字节记到自己的标签上，计划表打印每条规则的成本。默认集是 `*.lib`、`include/`、`__pycache__/`、`*.pyc`、`_archived/`、`*.map`、`.git/`、`node_modules/.cache/`；技能包另加它自带的两份 ffmpeg 可执行文件，因为工具包只发一份。来源目录下的任何字节都不会被删除，因此重跑是重新测量排除量，而不是继承一棵已经被瘦过的树。

**一个文件不能进两个包。** 一张共享的认领表以每个文件的 `realpath` 为键，存下认领它的 `<包>:<包内路径>`；第二个包再认领同一真实路径就抛 `PlanError`，在写出任何东西之前中止计划。包内出现重复的包内路径同样是错误，而不是静默覆盖。

**manifest 记录的是下载物。** 摘要在压缩之后、并与字节计数读同一条流，因此 `bytes` 与 `sha256` 描述的是盘上的 `.tar.zst`——也就是安装器要校验的东西——而不是未压缩的 tar。构建在它掌控的每个输入上都是确定的：条目排序，头部使用固定时间戳。

**tar 是每个成员头部紧跟其自身的包体。** 每个成员的头部之后立刻是该成员的字节，补齐到 512 字节边界；结束归档的两个全零块位于最后一个包体之后。超过 100 字节名字字段的路径拆到 155 字节的 prefix 字段，两者都放不下则报错，绝不截断。

## 考虑过的其他方案

**依赖仓库里的 `tar` 包。** 它在 `node_modules` 里，但只是 `apps/desktop` 的传递依赖，从 `scripts/` 引入会落到没有任何 manifest 声明的目录布局上。把它提升为根依赖，等于为「Node 自带 zstd 加一个两百行写入器」已经覆盖的格式新增一个依赖。

**在磁盘上直接瘦身开发者的目录。** 删掉 `.lib`、缓存与重复的 ffmpeg 副本会让每次打包都更省。但它同时会改动产品开发所在的目录，让结果取决于瘦身是否跑过，并把一个可回退的过滤决定变成不可逆的决定。

**整棵树压成一个扁平归档。** 单包会让 `unpackTo` 失去意义，也让 manifest 的逐包结构不再需要。但安装器的断点续传与逐包校验都是按文件计的，而 Python 包必须能单独重打，不必重新压一遍模型权重。

**用整份 `node_modules` 解析本体包的依赖闭包。** 直接拷贝仓库的存储会装进 1.49 GB 构建产物从未引入的包。闭包改为从每个包声明的运行时依赖解析，按 Node 自身的逐级向上查找，每个不同的已安装副本只在 `node_modules/<名字>` 下挂一次。

## 后果

四个小包已在本机构建并校验：技能 28,141,856 字节，ffmpeg 101,715,568，BGM 能力包 191,085,086，whisper 444,011,945，都与 manifest 相符，包名与计划表一致，sha256 由 `--verify` 重算。技能归档解出 348 个文件，字节长度与来源逐一相等。把其中一个包翻一个字节，`--verify` 便以非零退出并打印两个不同的哈希；把字节改回来，它又回到 0。

三个大包只做了计划、没有构建。本体包计划 39,682 个文件、391.6 MB 原始字节，来源是 `packages/*/*/{lib,package.json}`、`apps/cli`、`apps/web/dist` 与解析出的闭包；插件包 1,712 个文件、423.1 MB；Python 包在排除 855.6 MB 的 `*.lib` 与 map 文件之后是 29,664 个文件、1,558.8 MB。计划它们约需 40 秒且只读元数据，因此构建前先看一遍计划表成本足够低。

关于来源，有三件事与打包清单的估算不同，值得记下来。`apps/web/dist` 与工作区已构建的 `lib/` 合计 81.2 MB，所以本体包的体积来自它的依赖闭包，而不是构建产物。ffmpeg 两个二进制分别是 156.73 与 156.53 MB，排除技能树里的两份省下 193.3 MB。本机的技能树根本没有 `_archived` 目录，因此那条默认规则当前一个字节也没排除。

本体包与插件包在构建之前无法验证：它们只经默认规则集检验过排除，且本体包的闭包尚未证明能启动产品。Python 包对 `include/` 与 `*.lib` 的排除同样只是计划，未对照一个能用的解释器验证——而那正是自检文档自己列出的前提。

## 测试

`pnpm exec oxlint scripts/release/pack-release.ts scripts/release/tar-zstd.ts` 无任何发现，`tsc -b tsconfig.host.json` 对这两个文件无报错。验收路径就是这三种模式本身：`--plan-only` 打印七行计划表并以 0 退出；`--build --only <包>` 写出的归档，其 `bytes` 与 `sha256` 由 manifest 记录；`--verify` 在包与 manifest 相符时以 0 退出，在翻转某个包一个字节后以非零退出并点名两个哈希。此外每个已构建的包都用平台 `tar` 读过：成员全部列出，技能包解出 348 个文件且与来源相符。
