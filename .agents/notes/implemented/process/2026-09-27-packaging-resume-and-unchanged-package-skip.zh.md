# Agent Note: 从失败的那一步续跑打包，并只重打变化的部分

Status: implemented

[English](2026-09-27-packaging-resume-and-unchanged-package-skip.md) | 中文

## Problem

`pnpm run package:desktop:win:x64:unsigned` 要跑十三个步骤（S1–S13），而且没有续跑入口：无论 S6（钉住的社区插件拒绝当前 Host 版本）还是 S12（`prepare:dsh`）失败，操作者唯一的重试方式就是重跑整条 20–25 分钟的流水线，而这次重试会先把与上次逐字节相同的 tarball 重打一遍，才走到先前失败的那一步。

打包从工作树取输入，而不是从一个提交取输入，而没有任何地方写明这一点。仅一天之内就有两个安装器因此作废。一次只重跑 S12 的运行吸收了另一位作者尚未提交的改动，因为部分重跑的流水线读到的是树里当下有什么。另一次运行产出的 drama tarball 写于 15:32，而它本应携带的修复提交于 15:39，于是那个安装器既不包含已承诺的修复，也无法归因到任何提交，只能作废。

媒体载荷[早已有可用的模式](../../../../apps/desktop/scripts/prepare-media-runtime.ts)：已存在的载荷要先经过校验才会被复用，该步骤会打印 `existing payload verified and reused`。打包对其 tarball 没有对应机制。

## Decision

两项改动，都在打包流水线内，都以拒绝代替警告。

**带前置校验的续跑（`--from`/`--only`）。** [`package-steps.ts`](../../../../apps/desktop/scripts/package-steps.ts) 持有步骤表——十三个步骤、各自的名称，以及每一步产出的路径——[`package-target.ts`](../../../../apps/desktop/scripts/package-target.ts) 提供每一步的命令。`--list-steps` 打印这张表，于是「步骤与产物」的对应关系只有一个归属地，不会漂移进散文。

一次运行随后遵守四条规则，全部由代码而不是 runbook 强制执行：

1. 除非 `git status --porcelain` 除 `.pi-glla/`（harness 自身纳入版本管理的运行时状态）之外为空，否则拒绝启动。
2. 启动时读取一次 HEAD，并在每一步之前重新读取，一旦变化即拒绝。
3. 在第一步之前打印被跳过步骤留下的每个产物，各自带路径、写入时间、字节数或目录条目数、SHA-256 摘要，以及一个命名整组的摘要。
4. 拒绝早于 HEAD 提交时间的被复用产物，并点名该产物、它的写入时间与提交时间。

续跑要求**每个**被跳过步骤的产物都存在：缺失的产物或早于提交时间的产物都会让运行在开始前停下。失败消息会点名该步骤，以及可用于续跑的 `--from <S#>`。

**按内容哈希跳过未变的包。** [`pack-plan.ts`](../../../../scripts/release/pack-plan.ts) 对 `pnpm pack` 读取的文件——manifest 的 `files` 模式、npm 总会打包的名字，以及 `main`/`bin` 目标——连同包管理器与该成员整个同族依赖闭包的输入摘要一起求摘要。[`pack.ts`](../../../../scripts/release/pack.ts) 在记录中的摘要仍然吻合、记录里的 tarball 内容哈希仍与文件一致、且记录中的输入覆盖了打包载荷时，保留该 tarball。每个判定都会打印成员名、摘要和产物路径；记录写在 tarball 旁边的 `release-pack-<family>.json` 中。

让部分复用保持一致的是依赖闭包。消费方自身的字节不会因为某个依赖被重打而改变，但一次发布打包的是一个提交：由新内容打出的依赖意味着消费方是在那份内容存在之前打出的，因此它的摘要会变化并被重打。

打包步骤保持它原有的发布边界位置——它从一个提交产出全部 tarball，并把恰好那些字节交给发布步骤（该边界由[发布序列决策](2026-08-10-npm-release-sequences.zh.md)持有）；本决策改变的是其中哪些 tarball 会被这次运行重写。

## Alternatives considered

**用运行状态文件记录已完成步骤。** 归因能力强于步骤表——记录可以写明每个产物是由哪个提交构建的。但它引入了必须与 tarball 保持同步的持久状态，而且手工 `rm` 之后记录会撒谎，因此运行仍然需要今天承担判定的那三项检查：工作树、HEAD 与新鲜度。

**按 mtime 复用。** 更省事也更熟悉，而事故正好说明了它为何失败：那个 drama tarball 比它所依据的源文件更新，却比它本应携带的修复更旧。时间戳只能回答「何时」，永远回答不了「由什么」。

**对打包后 tarball 的载荷求哈希，而不是对输入求哈希。** 原则上完全正确，但载荷只有在打完包之后才存在，因此无法用来决定是否要打包。

**不接步骤参数的 `--resume`。** 它需要被否决的那套运行状态；而失败消息点名的 `--from <S#>` 用无状态的方式给了操作者同样的一条命令恢复。

**精确复刻 npm 的文件选择。** 我们拒绝重新实现 npm-packlist 的规则，改用超集：声明为目录的路径贡献其整棵子树，`readme|copying|licen[cs]e|notice|changes|changelog|history` 这些名字始终加入。多算只会多打一次包，少算则会复用一份其未被记录的文件已经变过的 tarball。记录里的 `inputsMatchPayload` 标记让方向可观测：以打包好的 309 个 dsh 同族 tarball 与 9 个 vendor tarball 实测，309 个成员中有 308 个被完全覆盖，而 `@deepseek-ai/dsh-experimental-webworker-packer` 每次运行都会重打，因为 `pnpm pack` 会额外加入一个其 `files` 模式未选中的 `lib/types/bin.js`。

## Consequences

S13 失败后的重试现在是分钟级，而不再重建二十分钟的前缀；可复用的前缀连同标识它的摘要一起被打印出来。在实测情形下——309 个 dsh 成员、当前提交下有 21 个发生变化——打包步骤从重打每一个成员变成只重打那 21 个，是秒到分钟级的墙钟时间，而非整轮打包。事故所需的同提交重跑（签名、公证或 NSIS 失败后的 `--from S13`）则完全跳过打包。

代价是：任何提交都会让复用集合失效，包括只改文档的提交，因为它让 HEAD 越过了那些 tarball，于是其后的续跑会重打。这正是预期的方向——打包一棵没有任何提交命名的树，正是作废那个安装器的原因。

这些规则约束的是字节**来自哪里**，而不是它们**包含什么**：在一个提交上干净的工作树，仍然是一次续跑所能证明的全部。
