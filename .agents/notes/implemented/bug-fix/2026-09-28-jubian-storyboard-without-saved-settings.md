# Agent Note: Reading a storyboard that has no saved settings

Status: implemented

English | [中文](2026-09-28-jubian-storyboard-without-saved-settings.zh.md)

## Problem

The 2026-09-27 field report listed `storyboard get` and `prepare_video` failing on every id with `Jubian response did not match the expected envelope`, including the stub `1699732` the reporter had just created through `jubian_storyboard create`, while the same account's workbench displayed that board. A `DSH_JUBIAN_DEBUG_DUMP` capture of that exact read settled which layer refused: HTTP 200, application code 200, an ordinary object payload of 426 bytes, and `modelConfig: null` inside it. The envelope was never the fault. `readStoryboard()` in `@deepseek-ai/dsh-jubian-api` required `modelConfig.ratio`, `modelConfig.resolution`, `modelConfig.genNum === 1` and an integer `modelConfig.duration`, and `storyboardMaterials()` refused a `storyboardMaterialList` that was neither an array nor JSON text. A model setting is a choice someone saved, so a storyboard nobody has configured returns no `modelConfig` at all: the reader refused a payload the provider legitimately holds, and the refusal named only the envelope it did not match. The one detail that survived the report's other failing reads — `Expected a JSON object` — is what `object()` in `tool-jubian/src/model-settings.ts` produces for a `modelConfig` that is not an object, so at least one live read had already returned one.

## Decision

**A missing setting is substituted and reported; a value the provider sent must be usable.** `readStoryboard()` continues when `modelConfig` is absent, `null` or blank, substitutes `ratio: '9:16'`, `resolution: '720p'` and `genNum: 1`, and names every substitution in the new `StoryboardView.model_config_defaults` as wire field to substituted value. A field the provider did return is still checked: a blank label, a `genNum` other than 1, or an unreadable `modelConfig` string is refused. `duration` is never substituted, because the view reports it as `content_duration_ms` and the paid path compares it with the requested package; its absence leaves `content_duration_ms` null.

**The paid path refuses only what the provider must have saved, and says all of it.** `withGenerationEnabled()` returns the provider's own snapshot, so the provider generates from the `modelConfig` it stored and never from the values this reader substituted. `PAID_CONFIG_FIELDS` names the fields it acts on — `ratio`, `resolution`, `genNum`, `duration`, `modelId` — and the call raises `INVALID_ARGUMENT` when the saved configuration lacks any of them: a substituted label is this reader's default, and a missing `duration` or `modelId` would leave the provider choosing the length or the channel itself. The refusal states the expected wire fields, the ones the provider did not return, the redacted structure of the payload it received (`describeRejection()`, the same summary every reader rejects through) and the repair, `jubian_model preview → apply`. It does not send the caller to `prepare_video`, which reads the same `modelConfig` and refuses for the same reason.

**A field the provider legally leaves `null` is never a refusal reason.** The captured body carries `episodeCount`, `scriptName`, `remark`, `updateBy`, `updateTime` and `videoSubTaskList` as `null` beside an empty `storyboardMaterialList`, and each is legal. A reader requires the identity of the row it was asked about, the fields its own question is about, and nothing else: `readStoryboard()` requires `id`, `scriptId`, `isGenerate` and readable material keys; `readTaskPage()` requires only the task id, with `scriptId`, `episodeId`, `episodeCount`, `taskStatus`, `taskName` and all three cost fields read as nullable. That is why the report's `video task` (`1032840`) failure was not this defect: its reader never demanded a nullable field, and the dump showed the storyboard read failing on a payload the envelope had delivered intact.

**`storyboardMaterialList` is optional and read in both forms.** `null`, an absent key and a blank string are this provider's spellings of "no materials yet" and read as an empty list. Inline arrays and JSON text are both read, matching `storyboardMaterials()` in `native.ts`; a list that is neither is refused by name rather than silently reported as empty, which is what the previous `Array.isArray(...) ? ... : []` did while `prepare_video` read the same field strictly.

**Every refusal names the field it could not read.** `invalid()` in `storyboard.ts` takes a detail, so a rejection states `scriptId is not a positive integer`, `modelConfig.duration is not a positive whole number of seconds` or `storyboardMaterialList[0].materialKey is not a nonempty key`. The reader's name and the redacted payload structure are appended by `readPayload()` from [the diagnostics change](2026-09-28-jubian-unreadable-response-diagnostics.md), so the two layers cannot describe one body differently. `storyboardMaterials()` and `validatedVideoMaterials()` in `native.ts` name the field that blocks preparation, so `prepare_video` says whether the storyboard has no readable materials or no saved configuration.

## Alternatives considered

**Substitute `duration` as well.** Rejected: `content_duration_ms` is a caller-facing value the paid path compares with the requested package, so a substituted duration is an invented video length rather than a degraded field. A null states the absence instead.

**Keep `ratio`, `resolution` and `genNum` mandatory and report the storyboard as unreadable.** Rejected: those labels affect a generation specification and nothing the read exists to report. Requiring them made `storyboard get` unusable for every board created but not yet configured, which is exactly the state `jubian_storyboard create` leaves behind.

**Treat a blank `ratio` as unset.** Rejected: the provider sent a value, and substituting for a value this reader cannot use would replace a corrupt saved setting instead of reporting it. Only absence is substituted.

**Keep the silent empty material list.** Rejected: it reports a storyboard that has subjects as one that has none.

**Generate at the requested package length when the saved `duration` is absent.** Rejected: `content_duration_ms` is the caller's statement of what to generate, but the provider derives its own length from the `modelConfig` it stored, and the paid path verifies the saved duration against the requested package before enabling generation. Writing a duration the user never saved spends money on a specification this library chose, and it would still have no `modelId` to buy from — the field that actually blocks the call.

## Consequences

`packages/jubian/jubian-api/tests/storyboard.spec.ts` pins the captured body's structure with the reporter's account fields removed (`createBy`, `userId`, `companyId`, `mainDeptId`, `secondDeptId`) and nothing else changed: `modelConfig: null` beside an empty `storyboardMaterialList`, all six nullable siblings `null`, reading through with `model_config_defaults`, `model_config_notes` and a null `content_duration_ms`; the incomplete saved object substituted inline and as JSON text; the null payload of an id the provider does not hold described as received; the free save still echoing the provider snapshot; and the paid path refusing with the expected fields, the fields that were missing and the top-level keys of the body it refused. `pnpm vitest run packages/jubian` covers both packages.

What this change does not add: a second source of saved model settings. The provider's own `modelConfig` on the storyboard is the only place a chosen channel and length live — the short-drama settings section in `packages/drama/drama-settings` pins an image row and a budget, not a video channel — so a caller that finds `modelConfig: null` must save settings with `jubian_model preview → apply` (or pick the model for that board in the workbench) before either paid path can run. `prepare_video` and `submit_video` read the same field through `validatedVideoMaterials()`, so the repair is once per storyboard rather than once per method.
