# Agent Note: Look up a Jubian screenplay by name in the existing tool package

Status: implemented

English | [中文](2026-09-24-jubian-name-lookup-tool.zh.md)

## Problem

A Jubian production is addressed by a `script_id`, and the sessions that drive one usually start from a name: a person says "续跑《山海自有相逢处》", and the id the provider needs is not in the conversation. Nothing in the plugin could turn the one into the other. `jubian_catalog` `script` reads the identity of a screenplay whose id the caller already has, and `jubian_organize` `index` reads one project's assets by that same id. A session holding only a name therefore had to reach the provider's two lists on its own, with its own credential lookup and its own envelope parsing — which is what the pool workflow's own scripts do today. The two lists answer different questions: `/aigc/script/list` holds the caller's own canvas projects, and `/script/center/pool/list` holds the screenplays the account may claim, with `canClaim` and the claiming names on every row.

A wrong answer here costs more than an empty one. The id a lookup returns addresses every later call in the production, including the paid image, video and erasure paths, so a near-miss match would point a whole pipeline at another project with nothing in the transcript to show it. The pool list adds a second way to be wrong: a first-page-only read reports "not in the pool" for a screenplay that sits on page two, and the difference between "this name is not claimable" and "I did not finish reading" decides whether a production waits or claims a screenplay another group is already making.

## Decision

`@deepseek-ai/dsh-tool-jubian` gains one read-only tool, `jubian_find`, implemented in [`src/find.ts`](../../../../packages/jubian/tool-jubian/src/find.ts) and registered beside the eight tools the row already mounts.

It is a tool name inside the existing package rather than a method on `jubian_catalog` or a package of its own, because everything it needs is already built there. The row's single `JubianClient` supplies credential resolution (the credential store, then the workspace pipeline file), the origin, the timeout, envelope normalization and the five stable failure codes; a reader for the new lists is one more function in `dsh-jubian-api` beside the ones the other reads call. [The asset-organization decision](../feature/2026-09-21-jubian-asset-organization.md) took the same route for `jubian_organize` and for the same reason: a read that answers its own question gets its own name, so a model can choose it and read "this one changes nothing" in the description of the tool it is about to call.

`scope` is required and names exactly one endpoint: `mine` reads `GET /aigc/script/list`, `pool` reads `GET /script/center/pool/list`. A value that is neither fails as `INVALID_ARGUMENT` before any request leaves. `status` is a `pool` argument, forwarded verbatim as a query parameter; `mine` with a `status` is refused rather than silently ignored, because the caller's own projects carry no pool state and a dropped filter returns a wider list than the caller asked for.

The `mine` list is also where the console reads 漫剧 video projects from, so the tool passes the provider's own selectors through instead of inventing a third scope. An operator's captured console request for 漫剧视频 is `GET /aigc/script/list?pageNum=1&pageSize=40&productionType=0&shareTargetType=1` against the same endpoint `mine` already reads, discriminated only by those two extra query parameters; an offline scan of the provider's frontend bundle found no 漫剧 route separate from it, so a caller lists those projects by forwarding `production_type` as `productionType` and `share_target_type` as `shareTargetType`. The values are the provider's own codes: the tool validates only that each is a safe integer, interprets neither, defaults neither and omits an unsupplied one from the query rather than sending a default. They are `mine` arguments like `status` is a `pool` argument, and a `pool` call carrying either fails as `INVALID_ARGUMENT` before any request leaves.

`name` is optional, and matching is deliberately substring-only. The query and both row fields pass through the same trim, internal-whitespace collapse and case fold, and a row matches when `scriptName` or `manuscriptName` contains the result. There is no pinyin transliteration, no alias table and no edit distance: a name that differs from a stored one by a character is far more likely to be a different screenplay than a typo, and an empty `matches` list is the honest answer for a name neither list carries. Omitting `name` lists the scope's first page instead of failing, which is what a caller that wants to see the pool does. Only a payload the reader cannot read raises `CONTRACT_CHANGED`; "no such screenplay here" and "I could not tell" must never look alike.

The scan runs to the end of the list and reports how far it got. `page_size` (1..1000, default 20) bounds one request rather than the read: the call requests pages from `page_num` until the rows it has read cover the page's own `total`, an empty page arrives, or it reaches `MAX_SCAN_PAGES` (50), the bound that keeps a list the provider grows without limit from becoming an endless loop. The result carries `total` (the provider's own list size), `scanned_pages`, `complete`, `returned`, `truncated` (the `MAX_MATCHES` = 100 output cap) and `scan_page_limit`, so a caller can tell a complete empty answer from a partial one. The pool workflow recorded the same rule as measured evidence: `pageSize` is a per-request row limit while `total` is the size of the pool, and reading only the first page turns "the pool is larger than one page" into a silent miss ([api notes](../../../../packages/drama/skills/skills/jubian-snatch/references/api-notes.md)).

The two list endpoints belong to the provider's unwrapped family: they answer `{code, total, rows}` with no `data` wrapper, while the single-object endpoints this package already reads nest their payload under `data`. [`readScriptList`](../../../../packages/jubian/jubian-api/src/catalog.ts) accepts both spellings — the envelope's own keys, or the `data` they wrap — and requires an integer `total` and an array of rows. Anything else fails as `CONTRACT_CHANGED`, including a row without an id, because `total` is the only bound on how many pages remain unread and an empty list is a legitimate answer that must stay distinguishable from a parse that discarded rows. The unwrapped spelling is recorded as measured provider evidence in the same pool notes named above.

A match carries only the fields the reader actually read: `script_id`, `script_name`, `manuscript_name`, `episode_count`, `status` and `script_style` on every screenplays-list row, plus `can_claim`, `claim_leader_name` and `claim_member_name` under `pool`. A field the provider did not send stays `null` rather than being guessed. `script_style` is the provider's own `scriptStyle` code — the field that tells 真人 from 漫剧 — and it is returned only under `mine`: that is where the values were measured, and the pool's recorded field list carries no `scriptStyle` ([api notes](../../../../packages/drama/skills/skills/jubian-snatch/references/api-notes.md)), so a `pool` row does not carry the key at all. The tool sends `GET` requests only, writes no ledger line, checks no budget, takes no `idempotency_key`, and claims nothing: `can_claim` is the provider's own flag for the calling account, and moving a screenplay into a production remains the console's claim action.

## Alternatives considered

**A new `jubian_catalog` method.** The dispatch would work, and `jubian_catalog` already reads screenplays. It would also put a required `scope` beside a required `method` enum whose four other values ignore it, so one schema would carry two selectors and one description would have to separate a paged name scan from three account-level reads. A separate tool name keeps each schema one selector deep and lets the read-only, no-cost guarantee stand in the description of the tool it describes.

**A new package, `@deepseek-ai/dsh-tool-jubian-find`.** It would either rebuild what the row already has — credential resolution including the workspace fallback, the origin and timeout, envelope normalization, the error mapping — or depend on `tool-jubian` for them, which is the same code reached through a second mount and a second ledger root. The tool catalog's completeness guard would also boot one more package to publish one read.

**Pinyin, alias and fuzzy matching.** They would answer more questions and answer some of them wrongly. A returned id becomes the address of every later call in the production, so a match that is merely plausible is worse than no match: the tests keep the near misses explicit, and `山海相逢`, `shanhai` and `山与海` all return nothing against a stored `山海自有相逢处`.

**A third scope, or a dedicated 漫剧 endpoint.** The console reads 漫剧 video projects from the same `/aigc/script/list` as any other canvas project, discriminated by two query parameters, and the provider's frontend bundle carries no 漫剧 route of its own. A scope for it would either re-derive that endpoint under a second name or claim a route that does not exist; passing the provider's own selectors through states what the console actually sends and keeps the tool's one rule — one scope, one endpoint — intact.

**Returning the first page and letting the caller ask for more.** The provider's own default is one page, and the tool would return sooner. It would also have to explain that the match list is partial, because a caller cannot see which rows were never read; `total` beside `complete`, `scanned_pages` and `scan_page_limit` states that directly and costs the extra requests only when the list is larger than one page.

## Consequences

The registered tool set grows to nine, which is a fixed per-request token cost while the row is mounted and one more schema in the [tool catalog](../../../../docs/tool-catalog.md#deepseek-aidsh-tool-jubian). The read itself is free and leaves no ledger line, so a lookup before a paid call costs only its round trips.

Two limits are visible to a caller. A lookup can find only a screenplay the account can already see: it reads the caller's own canvas projects and the claimable pool, so a screenplay in neither scope is outside both. And it answers where a screenplay is, not whether the caller may use it: the pool's roles, claim conflicts and status transitions stay in the console and in the pool workflow, and `jubian_find` has no claim method. The 漫剧 selectors narrow what `mine` returns without reading anything about the project back: a row states its `script_style` code, and what any code means stays the provider's definition.

## Testing

`packages/jubian/tool-jubian/tests/find.spec.ts` (24 tests) covers both scopes, matching on either name field, the whitespace and case normalization, the near misses that must not match, the pool-only fields, `script_style` on every `mine` match, `status` forwarded on every page of a pool scan and refused for `mine`, `production_type` and `share_target_type` forwarded as the exact `productionType` / `shareTargetType` query the console sends, each forwarded alone with an absent one left out of the query, both refused for `pool` with a Chinese message, a non-integer code refused before any request, the exact path and method each scope requests, a scan that reads every page the total needs, the page bound that reports `complete: false`, the match cap, both envelope spellings, `CONTRACT_CHANGED` on a payload that is neither, and every argument refusal — none of which sends a request. `packages/jubian/jubian-api/tests/catalog.spec.ts` (16 tests, including the new `readScriptList` cases) covers the reader's two spellings, its required integer `total`, its field projection, the `null` it leaves for a field the provider did not send, the `scriptStyle` spellings it accepts, the flag spellings it accepts, and its rejections. `pnpm exec vitest run packages/jubian/tool-jubian/tests/find.spec.ts packages/jubian/jubian-api/tests/catalog.spec.ts --maxWorkers=1` reports 40 passed.

No call against the live provider was made while verifying this tool. The two paths, both envelope spellings and the 漫剧 query pair are the ones the pool workflow's notes and an operator's own captured console request record, and a provider change surfaces as `CONTRACT_CHANGED`, exactly as it does for every other reader in the package. What `productionType` and `shareTargetType` mean beyond the values the console sends is not verified, and the tool does not interpret them.
