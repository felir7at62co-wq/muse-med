# Muse accounts gateway

English | [中文](README.zh.md)

## Summary

This directory contains the separately deployed Muse account gateway. It serves account-scoped speech transcription, administrator-granted reference reading, and private script storage. Desktop and workspace packages do not launch it or store its Volcengine or TOS credentials.

## Administrator account overview

An account with `admin: true` can open `/account` → account management, or `/admin`, to see account state, linked Feishu names and organization identifiers, recent login and explicit task activity, and connected Desktop counts. Online accounts are deduplicated across computers; connections do not establish human interaction. Registered accounts include legacy and test accounts. Linked-user counts include accounts with a verified Feishu binding. Today and seven-day activity use the latest explicit task event in the Asia/Shanghai calendar and omit disabled accounts; historical activity before reporting was enabled is unavailable. Ordinary accounts cannot open the page. Viewing this metadata does not expose private conversations or manuscripts.

<a id="feishu-login"></a>
## Feishu login

Set `MUSE_FEISHU_LOGIN_CONFIG` to an absolute owner-only regular JSON file outside the release. Omit it to disable Feishu entry points. For internal use, configure `appType: "custom"` and set the app's availability to the enterprise members allowed to sign in. An existing bot app can add web capability; a custom app does not admit other enterprises or personal-edition users. `appType: "store"` is reserved for a separately published Store App, still subject to Feishu installation and availability policies. Set the app's redirect URL to the exact public origin plus `/auth/feishu/callback`. Enable its web application capability; basic login does not request phone, email, contacts, messages or `offline_access` scopes. When reusing an existing app, Feishu may display permissions the user previously granted; Muse uses only the login identity and does not persist Feishu tokens.

```json
{
  "appType": "custom",
  "appId": "cli_REPLACE_WITH_APP_ID",
  "appSecret": "REPLACE_WITH_PRIVATE_APP_SECRET",
  "redirectUri": "https://muse.aigc-pipeline.cn/auth/feishu/callback"
}
```

`tokenEndpointVersion` defaults to `"v3"`; `"v2"` explicitly selects the fixed v2 endpoint for compatibility. Muse never falls back automatically or reuses a failed authorization code; verify a selected version with a new authorization attempt. The [authorization-code documentation](https://open.feishu.cn/document/authentication-management/access-token/obtain-oauth-code) describes v2 for PKCE; [SDK issue #230](https://github.com/larksuite/oapi-sdk-go/issues/230) reports v3 `20049` failures with successful v2 comparisons, without official confirmation.

Optional policy fields are `requestTimeoutMs` (default 15000, range 1000–60000), `attemptTtlMs` (300000, range 60000–600000), `maxAttempts` (1000, range 1–10000), and `requestRatePerMinute` (60, range 1–1000). OAuth uses PKCE S256, single-use state and a browser-bound transient cookie; failed code exchanges are not retried. Only pages containing enabled Feishu authorization forms add the fixed `https://accounts.feishu.cn` origin to CSP `form-action` for OAuth redirects; other pages remain same-origin only. Keep callback query strings out of reverse-proxy access logs because they contain authorization codes and state. For Nginx, use an exact `location = /auth/feishu/callback` with `access_log off` and the existing gateway proxy settings. Tokens and application secrets stay on the server and never enter account records, Desktop credentials, model context or UI. Failure diagnostics contain only the phase, fixed error category, HTTP status, numeric provider code and elapsed time; they omit response bodies, identities and credentials.

When configured, Feishu is the only rendered sign-in action; login and registration pages omit username, password and registration forms. The legacy POST interfaces and account data remain compatible, and unconfigured gateways retain their existing pages. Ordinary Feishu users do not register a Muse username, set a password or bind an account. `GET /auth/feishu/start` starts web sign-in; `POST /auth/feishu/bind` remains available only from an authenticated, same-origin account page for explicit account continuity. Binding preserves the existing Muse ID, administrator flag, passwords and workspaces; a newly encountered identity creates an ordinary password-free account. Names and email do not merge accounts. Before enabling sign-in for the owner, bind the verified Feishu identity while authenticated as the existing `ylk` administrator; login order never grants administration.

Isolated local acceptance may use `http://localhost:<port>/auth/feishu/callback` or `http://127.0.0.1:<port>/auth/feishu/callback` only when `MUSE_ENVIRONMENT=development`, or when both library factories receive the explicit development environment. The registered callback must match the public origin exactly. Production still requires HTTPS; other HTTP hosts, user information and callback query strings are rejected. Secure, HttpOnly, `__Host-` cookies and OAuth checks remain enabled. Use a loopback-only listener with separate account and session files; do not redirect the production callback or reuse production writable data. Real provider acceptance and browser cookie behavior require local verification.

`POST /api/muse.activity` accepts only `{ "activity": "task-start" }` from an authenticated same-origin client and records server time for that account. The Desktop reports explicit user turns, excluding delegated agents, automatic goals, model retries and catalog refreshes; its report contains no task text or local paths. Reporting is best effort: offline or failed requests are neither retried nor backfilled. This is usage metadata, not an audit of all user actions. `MUSE_ACTIVITY_RATE_PER_MINUTE` sets the per-account/IP admission limit (default 120, range 1–10000). Account storage reads versions 1 and 2 and writes version 2 on mutation; follow the [account upgrade guide](../../docs/upgrade-guide/v0.2.1-alpha.1/muse-feishu-accounts/guide.md) before switching or rolling back gateways.

## Shared voice registration

Enable `POST /api/jubian/voice-slots` with `MUSE_VOICE_SLOTS_DIR`, an absolute private durable directory outside immutable releases. `MUSE_VOICE_SLOTS_LEASE_MS`, `MUSE_VOICE_SLOTS_LOCK_WAIT_MS`, `MUSE_VOICE_SLOTS_LOCK_POLL_MS` and `MUSE_VOICE_SLOTS_TIMEOUT_MS` configure reservation expiry, lock wait/polling and provider verification deadlines. The endpoint requires an active Muse cookie or Bearer session, same-origin mutation and a private `X-Jubian-Token`. Each operation verifies access to the fixed-origin exact Jubian project; ready/complete reads also require `delFlag=0` without conflicting deletion flags and verify the exact audio asset, canonical character/period tag and HTTPS URL. Provider credentials are never persisted or returned.

Actions are `acquire`, `start`, `complete`, `abandon` and `read`; the key is project/person/life period plus the original registration operation. An exclusive filesystem lock serializes writers across gateway processes. Only an unused reservation expires; a durable submitted operation never authorizes a second creation. Completion preserves its exact asset ID and cannot silently replace it. Unknown outcomes require original-operation reconciliation. Interrupted lock directories require operator inspection after the writer is stopped; do not erase submitted receipts or treat an expired login as permission to create again. Missing configuration returns 503. This service coordinates participating Muse clients; it does not stop provider UI or legacy writes and supplies no automatic asset deletion.

## Release inputs

Startup reports the actual loopback port after the gateway begins listening. `MUSE_PORT=0` lets the operating system allocate an available port for isolated deployment checks.

The gateway requires Node 22 or newer and the release-root DSH dependencies used by its account, model, and KB routes. Cloud workspace mode and administrator runtime contexts additionally require the matching `muse-runtime` and `global` release directories; desktop workspace mode does not start a cloud agent. Run `npm ci --omit=dev` in this directory after copying it into each new immutable release; `package-lock.json` pins the TOS SDK and WebSocket transport. `ffprobe` must exist on the server when ASR is enabled. Never copy account databases, KB vaults, credentials, or ASR job ledgers into the release tree.

### Desktop browser sign-in

`POST /api/desktop-login/start` issues a private redemption secret, public approval URL and matching code. Clients that send `provider=feishu` receive an entry URL that redirects directly to Feishu's official authorization UI when Feishu is enabled, without a Muse sign-in page. Requests without that field retain the original approval URL for older Desktop versions. OAuth retains PKCE and browser-bound single-use state, then returns to a MUSE device-confirmation page. The user checks the code shown in the Desktop and confirms with a same-origin POST before the device can sign in; a GET containing `desktop_login` never approves it. Unconfigured gateways keep password sign-in and explicit device confirmation. The earlier `/desktop-login` Feishu form remains compatible: its same-origin POST consumes a one-use intent bound to a separate HttpOnly browser nonce, so its callback can approve only that still-pending attempt without another confirmation. `POST /api/desktop-login/check` requires the original private secret, consumes approval once and issues an independent Desktop session through `Set-Cookie`. `POST /api/desktop-login/cancel` discards an unredeemed attempt. Credentials stay out of URLs and response bodies after issuance; approval and status responses disable caching. Cancellation, expiry or refreshing the authorization page invalidates its pending Feishu consent. Browser logout before redemption, password reset or account revocation invalidate approval. Browser and Desktop logout are independent after successful redemption.

Attempts are memory-only, expire after ten minutes and are bounded to 1,000 per process; the advertised polling interval is two seconds. The `desktopLoginOptions` factory argument can configure `ttlMs`, `maxAttempts` and `pollIntervalMs`. Gateway restart discards pending approvals, and an interrupted single-use redemption requires a fresh login. The existing durable session policy applies after redemption. Deploy gateway and Desktop changes together; no OS URL-scheme registration or local callback listener is required.

### Account sessions

The gateway resolves `MUSE_ACCOUNTS_FILE` to an absolute path and stores login sessions in `sessions.json` beside it. `MUSE_SESSIONS_FILE` can select another absolute path. Keep both files in the same private durable-data area outside immutable releases and backups exposed to users. Session writes use the account store's owner-only directory and atomic 0600-file pattern. The session file contains only SHA-256 token digests, account IDs, account revisions, and expiries; it never contains the bearer token or cookie value. Run only one gateway against a session file.

`MUSE_SESSION_TTL_MS` configures newly issued sessions from 60,000 milliseconds through 7,776,000,000 milliseconds (90 days). The default is 2,592,000,000 milliseconds (30 days): long enough for normal next-day Desktop recovery, but still bounded rather than permanent. Existing sessions keep the expiry recorded when they were issued. Expired records are omitted during startup and removed from the file. Logout, password change or reset, and every account enable/disable revision change revoke the affected records.

An absent session file is valid and starts empty, so deployments that omit the new settings retain their existing account configuration. A session that existed only in an older gateway process cannot be reconstructed; the first rollout can therefore require one login from existing users. Sessions issued after the durable store is active survive later gateway restarts and release-pointer changes. Preserve the session file during upgrade and rollback, and do not copy session data between development and production.

The service reads a private JSON file named by `MUSE_ASR_CONFIG`. Omit the variable to disable ASR; authenticated ASR calls then return 503. The file must be a regular file, mode 0600 on Linux, and contain these fields:

| Field | Use |
|---|---|
| `appId`, `accessToken` | Server-only credentials for the legacy single application. With a pool, retain the original application as `defaultPoolId`; a supplied top-level `appId` must match that resource. |
| `providerKind` | Legacy single-resource default: `standard` (1.0) or `flash`. Explicit resources declare their own versions. |
| `resources`, `quotaGroups`, `defaultPoolId` | Resources declare `poolId`, `appId`, private `accessToken`, `quotaGroup`, `maxConcurrentJobs`, and matching `serviceVersion`/`resourceId`. Groups declare `id`, shared `maxConcurrentJobs`, and optional daily limits. The default handles requests without a purpose and retains legacy ownership. |
| `routes` | Purpose map: `{ "subtitles": "flash", "screenplay": "standard-v2" }`; explicitly select `standard-v1` for compatibility. Mixed pools require these families and configured resources. |
| `speakerDiarization`, `speakerDiarizationVersion`, `speakerLongAudioSeconds` | Screenplay standard requests enable speaker separation by default, using version `200` and short/long mode split at 180 seconds. Disable explicitly or select `300` without the `200`-only mode. Available `speaker_id`, `additions.speaker_id`, and observed AUC `additions.speaker` values survive normalization; conflicting aliases fail the result; they identify voices within a task, not named characters. |
| Group `submitQps`, `queryQps` | Separate standard request frequencies, each defaulting to 10; their sum cannot exceed 20 QPS. These are not in-flight job counts. |
| Group `rollingAudioWindowSeconds`, `maxRollingAudioSeconds` | Optional paired ceiling across accounts and versions. Standard deployment uses 1,800 seconds / 1,800,000 audio seconds for the official half-hour / 500-hour audio submission limit. |
| `legacyAppId` | Original application ID for migrating receipts without resource fields. Defaults to the retained top-level `appId`; an explicit pool with old receipts must provide this referent, matching its default application. |
| `maxConcurrentJobs`, `maxQueuedJobs` | Global worker throttle and actual waiting capacity (default 20). Legacy workers default to 5 and cannot exceed 5. Pools derive capacity from groups and application/service pairs; a global throttle cannot exceed it. Standard workers hold slots until completion, including unknown outcomes; repeatedly confirmed terminal query statuses release the slot without resubmitting the original task. A full waiting queue returns 429. |
| `requestRatePerMinute` | Shared ASR submit/status requests per account/IP per minute, default 60. Size this above concurrent client polling demand; it does not alter provider submit/query QPS. |
| `maxPendingUploadsPerAccount` | Unfinished uploads per account (default 4). Requests wait for the previous account upload and quota reservation before staging; exceeding this bound returns 429. |
| `storageKind`, `gatewayStorage` | Standard storage: `tos` (legacy default) or explicit `gateway`. Gateway requires an independent absolute private `root`, HTTPS `baseURL` ending exactly `/api/asr/audio/`, and server-only `secret` of at least 32 UTF-8 bytes. Flash requires neither. |
| `accessKeyId`, `secretAccessKey` | Server-only TOS credentials, required only for standard `storageKind: tos`. |
| `bucket`, `region`, `endpoint`, `prefix` | With TOS: private bucket, matching official regional endpoint, and temporary prefix ending in `/`. |
| `root` | Absolute durable private directory for account-scoped job receipts and short-lived staged audio files, outside the release. |
| `ffprobePath` | Server-side `ffprobe` executable; it verifies codec and real duration for quota. |
| `timeoutMs`, `signedUrlTtlSeconds`, `pollIntervalMs` | Provider/verification timeout; signatures covering media duration plus one hour within seven days; standard query interval (default 5,000 ms, valid 1,000–60,000). |
| `maxAudioBytes`, `maxDurationSeconds` | Upload and duration ceilings. Flash also enforces 100,000,000 bytes / 7,200 seconds per request; standard duration stays within 18,000 seconds. Mixed pools may use the longer standard duration without widening flash limits. |
| `terminalQueryConfirmations` | Consecutive identical explicit terminal standard query responses required before failure releases a worker (default 3). Processing or unavailable query responses reset the count. |
| `maxDailySeconds`, `maxDailyJobs`, `maxActiveJobs` | Per-account billing ceilings. Compatibility `maxActiveJobs` remains 1; reservations are serialized. Accepted jobs may queue under shared worker limits. |
| `retentionSeconds`, `sweepIntervalSeconds` | Audio retention covers media duration plus one hour; standard retention cannot exceed its download signature lifetime. Cleanup interval is at least 60 seconds and no longer than retention. |

Standard audio uses private TOS or gateway storage. TOS preflight reads bucket ACL and policy, requiring owner-only grants and no Allow statement. Objects use a private ACL; unsigned GET must return 403 while signed range GET succeeds before billing. Failed preflight leaves a failed receipt without provider submission. Gateway storage checks its private directory at startup and waits until the listener is ready before recovering queued work.

Gateway storage serves signed GET/HEAD before account authentication at `/api/asr/audio/`; unsigned reads are forbidden. HMAC binds object UUID, expiry and content digest. Valid signatures support single HTTP ranges; replacing content invalidates earlier signatures. Completion, silence or retention expiry removes staged files while preserving receipts. Forward this route without logging query parameters (`access_log off`, or URI-only reverse-proxy logging). Signed URLs are temporary download credentials; no TOS account or client upload credential is needed.

The account-authenticated API accepts `audio/mpeg` and `audio/wav`, verifying MP3 or 16 kHz mono PCM16 WAV before billing. Both families durably queue private audio and return 202 independently of supplier completion; queued jobs appear as `processing`. Results contain second-based `start`, `end`, `text`, and optional `words`; blank and zero-duration punctuation words are omitted. Flash sends base64 `audio.data` directly without URL storage. Startup resumes unsubmitted flash work; interrupted durable `submitting` requests become `uncertain` and are never queried or automatically resubmitted. Invalid flash responses remain uncertain. Only pre-submit failures permit upload retry.

Standard 1.0 and 2.0 workers submit once and poll the original task through completion or silence. Provider code `20000002` reports `queued: true`; `20000001` clears that flag when recognition starts. Standard requests map Chinese to `audio.language: "zh-CN"`; automatic detection uses `request.enable_auto_lang`. Requests explicitly disable semantic smoothing (`enable_ddc: false`) to retain fillers and repetitions. Screenplay speaker separation uses the configured short/long non-meeting mode; voice labels do not establish character names. An active standard recovery worker holds its application/service/group concurrency slots while the task is processing or uncertain; startup restores the worker for the original task. Status reads do not issue extra supplier queries. Retention removes audio without authorizing another billable attempt or freeing an unresolved standard worker’s slots. An ended uncertain Flash request retains its original receipt and billing identity, with no active or restart-restored local worker; local worker absence does not establish supplier completion, cancellation, or refund. Daily and rolling-audio allowances remain governed by the receipt ledger. Investigate unresolved provider tasks before changing capacity. Receipts without `providerKind` retain standard 1.0 semantics; preserve their original storage and service definitions. Run one gateway per ledger and divide shared allowances between deployments. `close()` stops admission and polling, awaits owned operations, and does not cancel supplier tasks. Gateway `SIGTERM` and `SIGINT` stop new ASR uploads first, preserve signed-audio/status reads while owned responses settle, then close HTTP and model listeners. Repeated signals share one shutdown. Ledger worker failures and owned retention-cleanup failures are reported after resources settle; a rejected client upload does not itself make shutdown fail. Configure the supervisor stop timeout above the longest provider timeout plus upload and cleanup time; forcible termination cannot retain an unfinished Flash response.

A status read or retention sweep marks expired, unsubmitted waiting jobs as `failed` with `retentionExpired`, removes their staged audio and releases their waiting reservations without waiting for a worker. Their receipts retain the original task identity and report `inspect_receipt`, not an automatic upload retry. Admission, dispatch and waiting expiry are serialized; an already dispatched worker remains responsible for its own task and cleanup.

Flash uses the provider's default language detection for both accepted client values, `zh` and `auto`; it sends no explicit language option. Standard screenplay Chinese requests use the provider's default Chinese/English model so speaker separation remains available; legacy standard requests retain their language parameters.

A standard query returning `45000006` (source audio download failed), `45000092` (task absent) or `55001010` (task timed out) becomes failed only after `terminalQueryConfirmations` identical consecutive responses. The original receipt and task ID remain, a submitted failed key cannot submit again, and its reserved billing allowance is retained; this is not proof of a refund or charge outcome. Other unknown responses keep querying the original task. Dispatch selects an available resource within each account rather than allowing a blocked standard request to prevent that account's flash work.

### ASR application pools

Pool/group IDs are stable lowercase ASCII identifiers; application IDs accept ASCII letters, digits, underscores and hyphens without surrounding whitespace. Services are `flash` (`volc.bigasr.auc_turbo`), `standard-v1` (`volc.bigasr.auc`) and `standard-v2` (`volc.seedasr.auc`). Capacity identity is `(appId, resourceId)`; two keys for one pair declare the same group and concurrency. Keys never multiply group capacity. Only independently granted resource groups add worker capacity. Standard versions may share one conservative group across applications; its limit and the global throttle are explicit deployment configuration. Service-row and key counts do not establish independent supplier quotas.

Optional `X-Muse-Asr-Purpose: subtitles|screenplay` selects the server route: subtitles use flash, screenplay defaults to standard 2.0 in a mixed pool, and explicit configuration can select standard 1.0. Omission retains the default for existing clients. Each key permanently retains its original purpose, including omission; changes return 409. Route changes affect only new keys. Waiting and daily ceilings remain independent; deployment retains waiting 30 and daily 1,000 jobs / 180,000 seconds per account. Group daily ceilings reserve all accounts by UTC day. Rolling duration ceilings include unresolved charges and queued reservations across midnight, returning `provider_rate` before accepting a new billable receipt.

Reservation favors available application/service capacity. Dispatch rotates accounts, preserves waiting order within available resources and enforces resource/group/global limits. A queued request without a submission timestamp can move to a free application of its original service version after shared daily and rolling reservations are checked; rebinding is durable before provider dispatch. Purpose, task ID, audio digest and reservation timestamps remain unchanged. Submitting, processing and uncertain work always retains its original application and service. Startup validates all referents before adding missing pins to legacy receipts; original fields, provider kind and omitted purpose remain unchanged. Missing application fields require `legacyAppId` to match the retained default. Older single-application code cannot recover newer bindings. Missing resources or changed application/group/service/storage stop startup. Preserve definitions while receipts exist; private-ledger additions do not change released Session data.

Responses retain legacy status values, optional `queued: true`, and the actual `service_version`; purpose-aware requests also add `purpose`. Failures report `provider_rejected`, `provider_unavailable`, or pre-submit `storage_unavailable`. Optional `provider_diagnostic` contains validated operation, HTTP/provider status and the fixed reason `timeout`, `transport`, `http`, `response`, `json`, `result` or `audio`; historical missing reasons remain absent. `recovery` names the supported operation: poll the original standard task, wait for the current Flash response, inspect an ended unknown Flash receipt, use the result, or resume an unsubmitted upload with the same ID. It never authorizes another paid submission. Unknown Flash has no provider query; reading its unchanged server receipt cannot recover a lost synchronous response. Diagnostics establish neither charging nor refunds. Credentials, signed URLs, response bodies, raw exceptions and application identities never enter responses.

HTTP refusals retain `error` and add `error_code`: `queue_full`, `upload_busy`, `daily_quota`, `provider_rate`, `request_rate`, `server_draining`, `invalid_request` or `idempotency_conflict`. Queue/upload bounds and draining include `Retry-After: 2`; rolling allowance supplies its earliest retry interval. Submit and status share `requestRatePerMinute` requests per account/IP per minute (default 60) with `Retry-After: 60`; daily limits have no immediate retry hint. Retry unaccepted uploads with their original IDs after capacity clears. Accepted or unknown receipts require reconciliation, never a new-ID resubmit.

`GET /api/admin/asr/diagnostics` requires a signed-in administrator with active short-lived elevation and records access in the administrator audit log. Authorization is rechecked after audit persistence; a cancelled request does not read diagnostics. Its no-store response contains only in-memory aggregate counts and configured limits: active, worker and waiting occupancy; service-version and quota-group usage; age buckets for unresolved standard jobs; and `queue_full` categories observed since this gateway process started. It does not read or change receipts and never returns account, task, application, audio, path, provider-response or credential data. Counters reset when the gateway restarts.

No credential value belongs in Git, systemd `Environment=`, Desktop settings, logs, or model tool results. Both environments enable the KB machine endpoint with `MUSE_KB_VAULT` and a private `MUSE_KB_SECRET` file. Set `MUSE_KB_DOCUMENT_GRANTS` to an administrator-maintained regular JSON file outside the writable shared vault and outside editor-writable directories; on POSIX it cannot be group- or world-writable. An absent file path grants no shared documents. The gateway checks each shared document's full SHA-256 before search or reading. Do not copy the development vault into production based on its file count or titles. Without KB configuration, the route is absent; with it, an unauthenticated `/api/kb/mcp` request returns 401.

Set `MUSE_KB_USER_ROOT` to an existing, owner-only absolute directory outside the shared vault before starting a KB-enabled gateway. Missing, permissive, or overlapping roots stop startup. A signed-in account can submit 1–12 reviewed Markdown script sections per `ingest_script` call, with a 2 MiB request limit and a 400,000-character section limit. Each section stores its title, project-relative source identifier, and immutable text below the stable account ID; results report saved, duplicate, or failed sections separately. The account reads its own `private/SRC-...` IDs through `search`, `read`, and `read_opening`. Other accounts and machine tokens cannot read these private IDs. Muse recall uses directories, fulltext keywords, and page links; the MCP endpoint does not invoke semantic vectors. No video binary is uploaded through this tool. The server must be deployed and configured before Desktop can use this capability; source packaging alone does not activate it.

Desktop model access uses the same account session and global model directory as the website. `GET /api/desktop-models/providers` returns public metadata; `POST /api/desktop-models/:provider/chat/completions` accepts the session token as Bearer authentication and requires the configured public Origin. In the default `MUSE_DESKTOP_MODEL_TRANSPORT=relay` mode, upstream credentials remain on the server. Private `zhipu-official` credential arrays use the [shared model key pool](#model-key-pools) on both Desktop and cloud-workspace routes. Scalar credentials and other providers forward authenticated requests without a Muse-imposed per-account or shared concurrency cap; the Desktop route has no Muse model-request frequency limiter. Upstream provider rate limits and model output caps remain effective. Logout, account revocation, session expiry and client cancellation abort owned requests. Remove the retired `MUSE_DESKTOP_MODEL_MAX_ACTIVE` and `MUSE_DESKTOP_MODEL_MAX_TOTAL` environment settings before starting the gateway; their presence rejects startup with migration instructions.

Each global-directory model can declare `defaultReasoningEffort` as an enabled key from its `reasoningEfforts` map. Both relays map that default to the upstream wire value only when the request omits `reasoning_effort`; an explicit supported request wins. A missing default preserves the provider's default. GLM-5.3 requests retain thinking across tool continuations with `clear_thinking: false`; disabling its thinking is rejected. The configured `maxTokens` supplies an omitted output limit and caps larger requests, while an explicit smaller limit remains selected. Changing the directory requires a gateway restart when editing the private file directly; administrator settings updates apply live.

Upstream refusals expose fixed `error.code` and `error.message` values for authentication, quota, rate, context, output-limit, and invalid-parameter failures. Classification reads at most 64 KiB and never returns provider-controlled diagnostics or credentials. Mentioning quota without an exhaustion condition does not classify a request as exhausted quota. A validated integer `Retry-After` is retained for upstream 429 refusals. Unknown server failures return a generic error; terminal `finish_reason: length` still reports truncated output.

`MUSE_DESKTOP_MODEL_TRANSPORT=direct` explicitly enables supplier credential distribution to signed-in Desktop Hosts. New Hosts negotiate `X-Muse-Model-Access: direct-v1` on the metadata request, then retrieve the current catalog with private supplier addresses and keys from `GET /api/desktop-models/access`; both responses disable caching. Legacy clients keep their relay route. Direct access requires a complete native global directory: every model in a provider must resolve to its advertised ID, the same HTTPS API root and the same configured key. Zhipu key pools use the negotiated gateway route while other suppliers validate their direct credentials separately. Missing configuration fails rather than falling back to the cloud relay. The Host stores access in its account directory and calls suppliers directly; model bodies and SSE replies bypass this gateway. Account disable, expiry and logout refuse future access issuance, but cannot invalidate a copied supplier key or terminate a direct request outside Muse. Revoke or rotate that key at the supplier when required. This option does not provide supplier-enforced user quotas, temporary keys or request auditing. Never enable it for credentials whose distribution is not authorized.

The selected Muse account catalog supplies official DeepSeek Flash and V4 Pro, seven Yunying models including GLM-5.3-Flash, and official Zhipu GLM-5.3-Flash and FlashX as defined in [`selected-models.mjs`](selected-models.mjs). DeepSeek and Zhipu use separate official Chat Completions routes; Yunying uses the operator's existing API root. Each route has its own server credential reference, and users sign in to Muse without entering vendor keys. Desktop custom providers and the separate Codex subscription retain their own credentials and catalogs. Preparing this catalog does not deploy or activate it.

Run `node services/muse-accounts/prepare-selected-models.mjs` with absolute `--source` and `--output` paths; output must be outside repositories and distribution directories. The source is the existing version-two private model directory (`MUSE_MODEL_CONFIG` plus `.native`); the new output parent must already exist with owner-only permissions. Supply the DeepSeek key through an owner-only `--deepseek-key-file` or the operator process's `DEEPSEEK_API_KEY`. Supply one independent Zhipu key through operator `MUSE_ZHIPU_API_KEY`, or a pool through the JSON-array environment value `MUSE_ZHIPU_API_KEYS`; an owner-only `--zhipu-key-file` accepts one key per line, with a single line retaining scalar behavior. An existing private directory entry under `MUSE_ZHIPU_API_KEY` may likewise be a scalar or array. Yunying normally reuses an unambiguous existing endpoint and credential, with optional `--yunying-base-url`, `--yunying-key-file`, or operator `MUSE_YUNYING_API_KEY` overrides. Inheritance and overrides retain the verified Yunying origin; identical model IDs at another supplier do not authorize credential reuse. The command creates an exclusive 0600 candidate and an exact `.source-backup`, leaving the source unchanged. It rejects existing outputs and prints only model IDs, revisions, and file digests; never commit or package the candidate or backup.

Deployment must compare the current source to the receipt's `sourceSha256`, retain the private backup, atomically replace the server's `.native` file, and restart the gateway. Verify the signed-in catalog and real tool continuations before reporting availability. Rollback restores the exact private backup and restarts the gateway. This replacement removes every other shared model; an existing conversation selecting a withdrawn model must choose an available model. The selected capacities and output budgets follow the [model budget table](#selected-model-budgets); upstream limits still apply. The prepared catalog adds no concurrency cap.

### Model key pools

Zhipu array credentials share one gateway admission pool across Desktop and cloud-workspace requests. Desktop Hosts negotiate `X-Muse-Provider-Routing: mixed-v1`; Hosts also sending `X-Muse-Zhipu-Direct: leased-v1` receive `transport: leased` when gateway direct transport is enabled. Before each supplier call, these Hosts POST only `{model}` to `/api/desktop-models/zhipu-official/leases`, then send the conversation and stream directly to the returned supplier endpoint using a short-lived JWT. GET on `/leases/<id>` checks the same login; DELETE reports supplier-stream teardown. Older Hosts retain `transport: relay`, without receiving pooled keys. `MUSE_ZHIPU_KEY_CONCURRENCY` (default 20), `MUSE_ZHIPU_QUEUE_LIMIT` (1000), and `MUSE_ZHIPU_QUEUE_TIMEOUT_MS` (120000) apply to both transports. Queue overflow or timeout fails before supplier dispatch; an ambiguous acquisition is not automatically retried.

Direct reservations persist in private `model-direct-leases.json` beside the account file before credential issuance. Startup restores their credential-fingerprint counts before accepting traffic, including fingerprints temporarily absent from the current catalog. The file contains neither supplier secrets nor JWTs. `MUSE_ZHIPU_DIRECT_TOKEN_MS` (60000), `MUSE_ZHIPU_DIRECT_REQUEST_MS` (1800000), `MUSE_ZHIPU_DIRECT_CHECK_MS` (30000), and `MUSE_ZHIPU_DIRECT_GRACE_MS` (15000) configure token lifetime, maximum request duration, login checks, and release grace. Normal teardown releases after grace; missing completion retains the reservation until the original request deadline plus grace. Persistence failure stops further direct admissions. Keep the file across deployments; use one owning gateway process per shared key pool.

JWTs remain reusable bearer credentials until expiry: they are not supplier-enforced single-use or model-scoped grants. Login checks and client deadlines coordinate cooperative Muse clients; supplier-side cancellation and revocation of an already issued JWT are not guaranteed. Supplier-account entitlements remain authoritative, and other clients using the same credentials are outside the gateway's counts. Validate actual provider authorization and throughput before promising a user capacity.

Streaming relays forward unchanged bytes through a complete SSE `data: [DONE]` event, close the upstream response and request, and release admission after downstream completion. A `finish_reason` alone does not end forwarding: later tool-call chunks, other choices and usage remain available. Fragmented UTF-8, LF, CRLF and CR event separators are supported; a final CR terminates immediately, with its optional LF retained if already received. Streams without `[DONE]` retain ordinary EOF behavior; nonstream JSON is unchanged. Forwarded responses include duration-only `Server-Timing` fields: `gateway-queue` measures key admission when used, and `upstream-headers` measures dispatch to upstream HTTP headers, including connection setup. Neither measures model first-token latency or includes request content, account identifiers or credentials.

## Desktop website access

The gateway entry defaults to `MUSE_WORKSPACE_MODE=desktop`. Desktop installations connect through `/api/desktop/connect`. After browser login, `/` enters the sole online computer automatically or shows the computer picker when several or none are online. `/computers` always opens the picker, showing account-owned names, operating systems, online status and latest connection times. Ordinary browser access starts no cloud agent. Explicit `MUSE_WORKSPACE_MODE=cloud` retains hosted workrooms; the `createAccountServer` library factory retains that default for existing callers.

Explicit administrator account contexts use the existing runtime broker, named by `MUSE_RUNTIME_SOCKET` (default `/run/muse-runtime/broker.sock`), after independent-password elevation. Ordinary desktop routes neither start nor keep alive a cloud workroom. Each administrator context remains bound to its login, target and expiry; another account or later login cannot reuse its grant. These contexts do not change the user's desktop binding.

The desktop authenticates with its Muse cookie and installation UUID, and sends its hostname and operating system. Different installations remain connected simultaneously. Reconnecting the same UUID replaces only that installation's old connection. The account store retains offline devices and reads legacy `desktopDeviceId` records; older clients appear with a UUID-based name. Password reset, account disable, logout and expiry revoke the corresponding transport. Browser logout closes its observations without signing out a separately authenticated desktop.

HTTP uploads, event streams, Range responses and native `/api/remote.mux` frames use acknowledged chunks. Browser cancellation only detaches its local proxy; the relay never replays requests or cancels an agent turn. The desktop injects its own private Host cookie and loopback Origin, retaining Host trust checks. Gateway account/model/ASR/Wiki/feedback routes stay central; settings and custom providers belong to the desktop. Each browser tab uses `/desktop/<installation-UUID>/` for assets, HTTP requests and native WebSockets. The gateway verifies account ownership and strips the prefix before forwarding. Unselected requests fail with `desktop-selection-required` when several computers are online. Workspaces, files and sessions remain on their respective computers. The `desktopRelayOptions` factory argument configures transfer limits and `maxDevices` (20 retained installations per account by default).

The relay pings each ready desktop every `heartbeatIntervalMs` (15 seconds); a missing Pong within `heartbeatTimeoutMs` (30 seconds) removes its online status and closes its browser observations. The picker and entry page check status every five seconds while visible. The chat page names its computer; **切换电脑** opens the picker in a new tab, preserving the current tab. A disconnected tab waits for its original UUID even while another computer remains online. Disconnect and expired-login notices preserve the open workspace and unsent draft; reconnection removes the notice without reloading. Only complete, unencoded GET entry pages receive this observer; HEAD, partial responses, compressed content and event streams retain their bytes. A local Host response or WebSocket upgrade failure ends only the affected browser request; the desktop control connection remains available.

Desktop mode requires TLS reverse-proxy WebSocket forwarding to this process. Installing the client alone does not switch the deployed gateway. Local integration and Chromium tests verify computer selection, independent tabs, isolation, Range playback, cancellation and revocation; production mobile login and reverse-proxy operation require deployment verification.

Browser form pages use `Referrer-Policy: same-origin` so same-origin navigation POSTs retain their Origin for CSRF verification. Cross-origin and null-origin writes remain rejected. The repository install supplies `ws` for this fixture; standalone gateway deployments install this directory’s own dependencies. Run `node --test services/muse-accounts/desktop-{devices,remote,tunnel}.test.mjs` from the repository root for transport and store coverage; after building Host, Client and Web, run `pnpm exec vitest run --config vitest.web.config.ts apps/web/tests/muse-multi-computer.e2e.ts` for login, tabs, drafts and responsive UI checks.

## Muse LLM Wiki

Muse LLM Wiki uses the current Muse login through the existing `/api/kb/access` exchange. It requires no user API key or new storage root. The main Muse model reads original material and synthesizes linked Markdown through MCP; the gateway does not run a second model. Retrieval uses directories, fulltext keywords, and Wiki links. Gateway startup ignores `MUSE_KB_EMBEDDING_*`, `MUSE_KB_VECTORS`, and semantic scoring variables; existing vector files remain archival and are not opened. Compatibility `search` and `ingest` also use no embedding calls.

| Scope | Ownership and IDs |
|---|---|
| `private` | Default; current account only. Originals use `private/SRC-...`; pages use `private/wiki/concepts/...`. |
| `project` | Current account plus a safe `project_id`; IDs begin `project/<project_id>/`. Project IDs never select another account or a disk directory. |
| `shared` | Existing exact-byte administrator grants. Original IDs remain `SRC-...`; page IDs remain `wiki/...`. |

Use `wiki_capture_source` to preserve Markdown and create a source-page outline. A duplicate capture returns the existing immutable source ID. `ingest_script` retains reviewed-script validation and attempts the same source-page creation; its result directs the model to synthesis. The outline has status `skeleton` and contains a preview, without claiming that the source has been analyzed. Shared captures require an administrator account and a source grant before the source can be read or summarized.

Use `wiki_directory` to browse IDs and revisions, `wiki_search` for fulltext matches, and `wiki_read` for 6,000-character pages. Follow `next_start` to continue. Shared `wiki_search` and compatibility `search` match the complete authorized text of supported files up to 4 MiB. An opening-only shared grant stays limited to 24,000 characters. Private/project source reads use the existing immutable packets; `read` and `read_opening` continue to accept old private source IDs, and `read` also accepts private Wiki page IDs. `wiki_status` returns account, configured, private/project, and verified shared counts.

Use `wiki_write_page` after reading the relevant originals. Supply a scope-local `page_id`, title, synthesized Markdown, `expected_revision`, and `citations: [{id, start, end}]`. Citation offsets count Unicode characters; each range is at most 6,000 characters and must identify readable original material. Stored citations include the complete source SHA-256; displayed excerpts are recomputed from currently authorized originals. Derived text is limited to 100,000 characters. New pages use revision 0 as the expectation. Existing pages use the revision returned by a read or directory listing. Existing `[[concepts/name]]`, `[[entities/name]]`, and `[[sources/SRC-...]]` links support folder-qualified navigation; missing or ambiguous targets reject the write. Create each linked page before linking to it.

`wiki_history` lists immutable numbered revisions; `wiki_read` accepts a historical `revision`. Updating a legacy page preserves its complete prior text as revision 0. A process lock and revision check reject overlapping or stale writes; reload and merge the current page before retrying. A committed revision remains authoritative if its Markdown projection fails, and the write reports `projection_pending`. A lock left by a crashed writer requires administrator inspection. `wiki_links` returns outgoing links, backlinks, and citations, with truncation counts.

Ordinary accounts cannot write shared material, including through compatibility `ingest`; its machine token also requires an administrator account. An administrator can create a shared page from granted originals, or update an existing page whose current bytes have a full-read grant. Every shared page write returns `grant_update_required` and the new hash. The administrator must update the external grants file and restart the gateway before accounts can read the new bytes. Historical shared revisions are readable only when their exact bytes match the active grant. A write never expands account access.

`wiki_migration_preview` reports old pages, existing originals, and sources without outlines. It does not rewrite sources, move data, create grants, or claim synthesis. Existing source IDs and administrator grants remain valid. The link index, resolution, Unicode title normalization, and source-page outline adapt `@zosmaai/pi-llm-wiki` 0.6.3; [the pin record](wiki-upstream.json) records exact source-file hashes, and [the MIT notice](wiki-upstream.LICENSE) retains its copyright. Pi host hooks, QMD, and upstream model execution are not loaded.

Captures reject linked storage directories before writing and verify original bytes before accepting a duplicate.

`wiki_record_project` records planned or actual participation in the current account's private Wiki. Stable `project_key` (at most 75 ASCII characters) and `contribution_id` identify updates and retries; other accounts may use the same keys without sharing records. The tool preserves immutable evidence, writes a cited contribution, reads it back, and refreshes a browsable project overview. `synced` confirms both pages; `partial` means the contribution is saved but the overview requires retrying the same record. Status is an agent report (`completion_basis: "agent-report"`), not independent artifact verification. Edited contribution pages are preserved and require conflict resolution.

`wiki_project_portfolio` paginates recorded projects and status counts, or one project's work summaries, statuses and artifact references. Ordinary account sessions read only their own records. Set `MUSE_KB_PORTFOLIO_READERS` to an external, administrator-maintained JSON file containing `{ "version": 1, "accountIds": ["<16-character account ID>"] }` to authorize selected enabled accounts to read other enabled accounts' participation records. The file must be outside both Wiki roots, regular, and not group/world writable on POSIX. An absent setting grants no cross-account access; malformed configuration stops startup. General administrators and machine tokens do not automatically gain portfolio access. Results omit original sources, conversations and unrelated private Wiki pages. This authorization does not make private projects shared knowledge.

## Selected model budgets

`prepare-selected-models.mjs` prepares a private eleven-model directory without deploying it. [GPT Sol](https://developers.openai.com/api/docs/models/gpt-6-sol) and [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) use 1,050,000 context and 128,000 output tokens; [Claude Opus 5.5/Fable 5.1 and Sonnet 5.5](https://platform.claude.com/docs/en/models/overview) use 1,000,000 context and 128,000 output tokens. [Gemini 3.1 Pro](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-pro-preview) uses 1,048,576 context and 65,536 output tokens; the Yunying catalog declares text and image input for this model. [GLM-5.3-Flash and FlashX](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash) are listed with 1M context, 128K output, and text and image input; the catalog declares 1,048,576 context and a 128,000 output cap for each. Yunying Flash leaves reasoning effort to the supplier default; official Zhipu Flash and FlashX default to `max` with thinking enabled. Official [DeepSeek Flash/Pro](https://api-docs.deepseek.com/api/create-chat-completion/) use 1,048,576 context and 393,216 output tokens. GPT and DeepSeek default to low effort. These are model specifications, not an assurance that Yunying exposes every upstream capability. Verify the configured endpoints before deployment; short completions do not demonstrate full-window or full-output capacity. A finite output budget can still end with `max-tokens`; partial output stays in the session for continuation.

Cloud administrator model discovery uses the same pi-ai listing parser as local settings. Saved catalogs are readable without provider I/O; explicit endpoint probes pin public DNS, refuse redirects, and use the draft key or the named route's stored credential. Discovery returns candidates without changing configuration. The administrator selects and saves them before account catalogs include them. Failed probes return a safe field-level diagnostic and keep manual entry available.

## Verification and release

Run `node --test *.test.mjs` here; all provider and TOS operations in these tests are mocked. A real provider request is a separate authorized, billable integration check. Before cutover, save the current service unit and release pointer, keep the previous immutable release, and snapshot the job ledger and account state without exposing their contents. Stage development first, then production. Verify `/login` returns 200, unauthenticated `/api/kb/mcp` returns 401 when configured, and an authenticated GET of a random `/api/asr/jobs/:id` returns 404 when ASR is configured; 503 means it is disabled. With two test accounts, save one reviewed short script, confirm the owner can search and read its `private/SRC-...` ID, and confirm the other account cannot. Test a granted shared KB search and one separately approved short ASR fixture before declaring the service healthy. Revert the unit to its previous release if checks fail; retain the durable job ledger so already submitted task IDs can still be queried. Do not delete previous releases or temporary TOS objects as part of rollback.

`node verify-models-live.mjs <private-directory-file>` lists configured routes without making provider requests. After authorizing the billable check, add `--run` to test a tool call and its continuation through Muse's installed pi-ai serializer, with two concurrent models and a 45-second deadline per request. The probe requests `max_tokens: 32768`; acceptance and a short continuation do not establish that a model can produce that many tokens. Tool choice defaults to Muse's automatic selection; `--tool-choice=forced` checks an explicit named function instead. `--model=<id>` selects IDs and `--exclude-model=<id>` excludes them. Results contain fixed failure codes and token counts only; absent usage is `null`, including pi-ai's all-zero usage defaults. The probe neither changes the directory nor prints provider diagnostics, reasoning text, credentials, balance, or cost.

The service unit names are `muse-dev-accounts.service` and `muse-accounts.service`. Deployment tooling sets each unit's working directory to the new immutable release only after source and config checks pass. Durable account, ASR, and Wiki data stay outside that release. No deployment is performed by this directory.
